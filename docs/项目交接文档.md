# 甄客行项目开发交接

> 更新时间：2026-08-25
>
> 特别注意：本交接文档主要说明接下来要干什么，已经完成并验收的功能可以直接在本文档删除（此行禁止删除）。
>
> 当前实施口径：正式开始建设“甄客行”。甄客行不是以商城为主体的项目，而是一个类似大众点评的综合本地生活平台；第一阶段以平台首页和“甄客言”内容社区为主线，定位能力是核心基础能力，现有商城作为辅助交易模块继续保留和使用。

## 1. 产品定位与当前开发方向

甄客行面向本地居民、外地游客以及其他到访用户，承载城市内酒店、饭店、景区、商店和其他线下实体的发现、分享与点评。用户首先感知到的应当是一个综合本地生活平台，而不是一个被重新包装的商城首页。

当前阶段的产品主次关系如下：

1. **甄客行平台首页**：作为用户进入项目后的第一入口，承载轮播运营位、甄客言内容和必要的功能入口。
2. **甄客言**：作为第一阶段的核心内容功能，允许登录用户围绕酒店、饭店、景区、商店等本地实体发布帖子和点评。
3. **定位与地点**：作为甄客言及后续本地生活功能的公共基础能力，第一版先保证设备定位、当前市区显示、地点选择和导航正常；暂不使用定位结果过滤专区内容。
4. **用户视角身份**：发布甄客言时选择“本地土著”“外地人”等能说明体验视角的身份标签，帮助其他用户理解内容背景。
5. **商城**：保留现有完整交易能力，但弱化首页占比和平台心智，定位类似抖音、小红书中的商城——不是主体，但入口清楚、流程可用。

第一阶段目标是先把甄客行做出“本地生活内容平台”的基本样子和真实使用闭环，再根据实际业务逐步扩展酒店、饭店、景区等更深层的预订或交易能力。

## 2. 核心产品概念

### 2.1 甄客言

“甄客言”是登录用户主动发布的本地生活内容。它可以围绕酒店、饭店、景区、商店或其他线下实体，也可以表达对某个地点的真实体验、推荐、避坑信息或观察。

甄客言当前确定的基本特征：

- 发布者必须是已登录用户。
- 发布时必须选择或确认关联地点，地点是内容的重要组成部分。
- 发布时必须选择一个用户视角身份标签，例如“本地土著”“外地人”等；正式选项和文案后续确认。
- 内容不局限于商城商品，也不要求发布者必须先在平台完成购买。
- 内容可以关联酒店、饭店、景区、商店以及后续接入的其他本地实体类型。
- 用户应能在首页内容流中浏览甄客言，并进入独立详情页查看完整内容、作者视角和地点信息。
- 甄客言需要纳入平台审核、举报和内容治理，不能因为是用户发布内容而跳过管理。

标题、正文、图片或视频数量、评分维度、话题、评论、点赞、收藏和排序策略等细节，需在进入对应功能开发前继续确认，不能仅凭“类似大众点评”一次性照搬全部功能。

### 2.2 甄客言与现有甄客验的区别

甄客言与甄客验是相关但不同的两类内容，不能直接合并为同一概念：

| 对比项 | 甄客言 | 甄客验 |
|---|---|---|
| 内容定位 | 面向本地生活实体的主动分享、点评和讨论 | 基于真实购买或试用履约形成的体验内容 |
| 发布资格 | 登录用户，不以平台订单为前提 | 继续按现有真实订单、试用、收货或核销资格判断 |
| 关联对象 | 地点或本地实体是核心关联对象 | 订单、商品或试用履约记录是可信资格来源 |
| 身份表达 | 发布时选择本地人、外地人等体验视角标签 | 继续突出已购买、已试用或已核销等履约背景 |
| 主要作用 | 丰富城市内容，帮助用户发现和判断本地实体 | 证明一段与平台交易或试用相关的真实体验 |

现有甄客验流程继续保留。后续可以讨论两类内容是否在同一个内容流中展示，但必须使用清楚的类型标识，不能把普通甄客言伪装成“已消费”或“已验证”内容。

### 2.3 本地实体与地点

甄客行后续所有本地生活内容都需要围绕统一的“地点/实体”概念逐步建设。酒店、饭店、景区、商店首先是不同实体类型，不等于第一阶段必须同时建设四套独立交易系统。

地点能力至少需要表达：

- 地点名称、实体类型和公开地址。
- 经纬度以及地图服务使用的坐标体系。
- 所属城市、区县等必要地域信息。
- 地图选点、关键词搜索和当前位置附近选点。
- 地点详情与相关甄客言之间的关联。
- 用户端打开地图或导航的能力。
- 地点不存在、重复、迁址、停业或信息错误时的治理方式。

位置数据必须由后端按可信规则保存和校验，不能只依赖前端显示文本。涉及用户实时位置时必须先取得授权，并遵循最小采集、用途说明和隐私保护要求；公开帖子默认展示关联地点，不应直接暴露用户发布时的个人精确轨迹。

### 2.4 用户视角身份标签

“本地土著”“外地人”等属于内容视角标签，用于说明发布者是以什么背景体验该地点，不是系统角色、后台权限或身份认证等级。

第一阶段原则：

- 发布甄客言时必选一个视角标签。
- 标签要短、易懂，并能帮助阅读者判断内容视角。
- 标签选项由平台统一维护，不能让用户任意输入后伪装成官方身份。
- 标签不授予商家管理、审核、核销或其他后台权限。
- 是否允许用户长期保存默认标签、每篇内容单独选择，以及是否需要认证“本地人”，进入详细设计时再确认。

## 3. 甄客行首页

甄客行首页替代“商城首页是项目唯一主入口”的旧口径。首页首版按以下信息层级设计：

### 3.1 左上角当前市区

首页左上角默认展示根据设备定位得到的当前市区，让用户明确感知甄客行具备真实定位能力：

- 首次需要定位时按浏览器或微信环境正常申请用户授权。
- 定位成功后显示当前市区，并保存业务需要的城市、区县和坐标信息。
- 定位失败、用户拒绝授权或地图解析失败时，需要提供明确提示和手动选择城市的降级方式，不能让首页无法使用。
- 第一版的当前市区主要用于位置展示、选点基础和后续能力准备，**不得据此过滤本地专区、外地专区或首页甄客言内容**。
- 用户在北京、邯郸或其他城市看到的专区内容，第一版不因设备当前位置不同而出现数量差异或空白专区。

### 3.2 轮播运营位

首页上方展示轮播图，用于平台运营和项目导流：

- 每个轮播项至少包含图片、标题、跳转类型、跳转目标、排序和启停状态。
- 可以跳转到甄客行内部页面，也可以跳转到经过后台配置和校验的其他项目链接。
- 赛事链接可以作为“其他项目外链”的示例，但这不代表赛事成为甄客行自身业务模块，也不在甄客行内建设赛事功能。
- 外链需要明确的安全校验、可用性检查和适合当前浏览环境的打开方式。
- 后台应能配置轮播内容、顺序、有效期和跳转目标，不能将运营链接长期硬编码在用户端。

### 3.3 甄客言专区与内容区

轮播图下方以甄客言为首页主体内容，让用户进入首页后直接感知城市生活内容。甄客言可以设置“本地专区”“外地专区”等专区入口，专区名称、样式和切换交互需要正常呈现。

项目启动初期采用冷启动内容策略：

- 本地专区、外地专区等专区可以正常进入和浏览。
- 第一版所有专区使用平台级内容池、运营内容池或后续明确的非地理分区规则，不按设备当前位置自动筛选。
- 第一版也不因为帖子关联了某个城市，就自动把它限制在该城市用户的本地专区中。
- 不能出现“邯郸内容较多，但北京用户进入本地专区后什么也看不到”的情况。
- 当前市区、帖子关联地点和专区内容分发是三个独立概念；前两项第一版真实可用，第三项暂不启用地域关联。
- 页面文案和交互不得声称已经实现“只看当前城市”或“附近真实内容”，避免向用户表达尚未实现的地域筛选能力。

首版至少需要形成以下闭环：

```text
浏览首页甄客言
-> 进入甄客言详情
-> 查看作者、视角标签和关联地点
-> 从地点信息进入地图或导航
-> 登录用户进入发布页
-> 选择地点和视角标签并提交内容
-> 内容按审核规则进入可展示状态
```

内容卡片和详情页需要优先突出内容本身、作者视角和地点关系。商城商品或购买入口只有在内容确实关联商品时才作为辅助信息出现，不能占据每条甄客言的主体位置。

### 3.4 功能入口

首页可以保留商城，并为酒店、饭店、景区等本地生活内容提供发现入口，但第一阶段不为了填满页面制作无真实数据、无真实页面的假模块。

入口设计原则：

- 甄客言和本地地点发现优先。
- 商城入口清楚但弱化，不再把商品瀑布流作为平台首页主体。
- 酒店、饭店、景区等入口先连接真实地点和内容；具备真实交易能力时再显示预订、购票或套餐能力。
- 所有入口使用正式路由和独立页面，刷新、分享和登录回跳后仍能恢复当前页面。

## 4. 甄客言首版业务闭环

### 4.1 发布

甄客言首版发布流程至少包括：

1. 检查登录状态，未登录用户完成登录后返回发布流程。
2. 用户选择或搜索一个关联地点；需要定位时先申请定位权限。
3. 用户选择一个体验视角标签。
4. 用户填写内容并按后续确定的规则添加图片或视频。
5. 前端进行必要提示，后端重新执行身份、字段、地点、媒体和内容安全校验。
6. 保存内容及其作者、地点、视角标签、审核状态和时间信息。
7. 根据审核规则决定立即展示、机器审核后展示或人工审核后展示。

发布成功必须以服务端真实保存结果为准，不能使用本地数组或仅修改前端状态模拟成功。

### 4.2 浏览与详情

- 首页和列表只展示符合公开条件的甄客言。
- 内容详情使用独立正式路由，支持刷新和分享后直接打开。
- 详情明确展示作者、发布时间、视角标签、关联地点和内容类型。
- 地点信息可以进入地点详情、地图查看或导航。
- 删除、隐藏、审核拒绝或地点失效后的内容应有明确状态，不能继续通过旧链接泄露。

### 4.3 内容治理

首版必须同步考虑管理端能力：

- 查看、筛选和审核甄客言。
- 处理违规内容、下架内容和用户举报。
- 管理视角身份标签和可用状态。
- 处理错误地点、重复地点和恶意定位关联。
- 保留必要的审核记录和操作日志。

评论、点赞、收藏、关注、评分体系和推荐算法是否进入首版，后续按明确优先级决定；这些能力不能阻塞“发布—审核—展示—地点关联”的最小真实闭环。

## 5. 商城在甄客行中的位置

现有商城是已经完成且仍然有用的交易模块，不能删除、废弃或破坏。新的产品关系是“甄客行包含商城”，不是“商城等于甄客行”。

### 5.1 继续保留的能力

- 商家入驻、审核和公开店铺资料。
- 商品发布、审核、库存、购物车和优惠能力。
- 订单、支付、退款、发货、收货和线下核销。
- 线上/线下试用及其履约流程。
- 基于真实购买或试用资格的甄客验。
- 超管端和商家端已有管理能力。

### 5.2 产品上的弱化方式

- 平台默认首页改为甄客行首页，不再默认展示完整商城首页。
- 商城保留独立正式入口和原有完整页面。
- 首页可展示少量与内容或运营主题相关的商品，但不能压过甄客言内容主线。
- 甄客言可以关联地点；是否关联商城商家或商品是可选的辅助关系，不能成为发布前提。
- 从甄客言进入商品购买时继续走现有可信订单、支付、退款和核销流程。

## 6. 用户、商家与地点关系

### 6.1 用户

现有商城用户作为甄客行平台用户继续使用，不做无意义的重复账号建设：

- 保留现有用户 ID、手机号、密码、登录态和交易关系。
- 在同一账号下增加甄客言发布、内容管理和地点互动能力。
- 用户视角标签是内容属性或用户偏好，不得混入后台 RBAC 权限。
- 用户个人主页后续需要区分其甄客言、甄客验和交易相关内容。

### 6.2 商家与普通地点

- 已入驻商城的商家可以与甄客行地点建立可信关联，但不能只按名称自动认领。
- 用户可以点评尚未入驻商城的线下实体，平台内容覆盖范围不应被商城商家范围限制。
- “平台地点”“已入驻商家”“可交易店铺”是不同状态，用户端必须使用清楚标识。
- 商家认领地点、纠错地点、回应内容等能力，需要独立需求和可信审核，第一阶段不得默认把普通用户提交的地点直接交给同名商家管理。

## 7. 定位能力建设原则

甄客行后续会高度使用定位，因此定位不能只作为发布表单中的一个普通文本框处理。

当前建设原则：

1. 统一封装浏览器、微信环境和地图服务之间的定位与坐标转换。
2. 区分“用户当前定位”“用户选择的地点”“帖子公开展示的地点”，三者不能混为一个字段。
3. 发布甄客言时保存关联地点的稳定标识，并保存业务需要的地点快照，避免地点改名后历史内容无法理解。
4. 前端定位失败、拒绝授权或精度不足时，应允许用户通过地图或关键词手动选点。
5. 后端校验地点存在性、坐标格式和关联权限，不能信任用户提交的地点名称与坐标组合。
6. 对用户位置采用最小权限、最短必要保存和明确用途说明，不记录与业务无关的持续轨迹。
7. 未来的附近内容、距离排序、城市切换和区域筛选应复用同一套地点基础能力。

### 7.1 第一版定位与专区解耦规则

第一版必须同时满足“定位是真的”和“专区不按定位过滤”：

```text
设备定位 -> 首页左上角显示当前市区，并服务于发布选点、地点详情和导航

本地专区 / 外地专区 -> 正常展示甄客言，但暂时不读取设备城市作为内容筛选条件
```

实现时不能为了省事返回假城市，也不能因为已经拿到真实城市就提前给专区 SQL、接口或前端列表增加城市过滤条件。接口和数据模型可以保留未来地域分发所需的城市、区县和地点字段，但第一版专区查询默认使用全平台可展示内容范围。

后期只有在帖子数量和城市覆盖能够支撑稳定内容供给后，才启动真正的本地专区。启用前需单独确认内容量门槛、城市切换、当前位置与用户手选城市的优先级、无内容时的跨城兜底以及历史帖归属规则，不能仅通过打开一个城市筛选开关直接上线。

项目现有腾讯地图地址解析、商家详情和导航能力可作为基础，但在复用前必须检查其当前接口范围、浏览环境兼容性和位置隐私边界。

## 8. 第一阶段范围

### 8.1 第一阶段应完成

- 甄客行平台首页及正式路由。
- 首页左上角真实定位并默认显示设备当前市区，同时提供失败后的手动选择降级。
- 后台可配置的首页轮播图和内外部跳转。
- 甄客言列表、独立详情页和登录用户发布页。
- 本地专区、外地专区等专区入口和正常内容展示，但专区查询暂不关联设备定位或帖子所在城市。
- 地点搜索、定位选点、地点关联及必要的地图/导航入口。
- 发布时必选的用户视角身份标签。
- 甄客言的服务端保存、审核状态和管理端治理入口。
- 首页从商城主导调整为甄客言主导，同时保留商城正式入口。
- 现有甄客验与甄客言在概念、资格和展示标签上的明确区分。

### 8.2 暂不因本轮需求自动扩展

- 完整照搬大众点评的所有评分、榜单、会员、广告和推荐算法。
- 同时建设酒店选房、景区实名票务、饭店订座排队等完整交易系统。
- 仅为了平台化而大规模重命名现有数据库表或拆分现有商城代码。
- 跨城市运营体系、城市加盟体系和完整多租户改造。
- 未确认规则的达人认证、本地人认证、等级成长和商业推广体系。
- 将轮播外链所指向的其他项目建设成甄客行内部业务模块。
- 第一版不启用“本地专区只显示当前城市帖子”、附近距离排序或按城市隔离内容池。

多租户仍放在较后阶段。只有平台、内容、地点和多个真实业务模块稳定后，才能基于可信租户上下文设计数据库、权限、配置、缓存、文件、任务和审计隔离。

## 9. 工程基线与开发约束

| 模块 | 目录 | 当前职责 |
|---|---|---|
| 后端 | `delivery-backend` | Spring Boot、MyBatis、MySQL、Redis |

| 用户端 | `delivery-frontend` | 甄客行用户端和现有商城用户端的唯一维护目录 |
| 管理/商家端 | `delivery-admin-frontend` | 超管、内容治理和商家后台 |

后端继续采用模块化单体，标准调用方向为：

```text
controller -> service -> mapper/XML -> domain/dto/vo
```

开发约束如下：

- 先检查现有用户、媒体、地图、商家、审核、评论和甄客验能力，再决定复用或增加最小新模型。
- 甄客言必须使用真实后端接口和持久化数据，不得使用 mock、本地数组或仅修改前端状态模拟成功。
- Controller 负责接口和基本参数接收，Service 负责身份、事务、资格和状态，Mapper SQL 负责归属、期望原状态和并发条件。
- 用户身份、地点、商家关系、审核状态和目标状态均不能信任前端提交，必须由服务端重新确认。
- 新页面使用正式独立路由和页面文件，保证刷新、分享、登录回跳和浏览器前进后退可用。
- 不破坏现有商城历史数据、订单、支付回调、退款、分享链接和核销闭环。
- 数据库变更只新增版本化增量脚本，不改写已执行的历史脚本；是否保留脚本按当前项目约定执行。
- 上传媒体、定位数据、用户资料和联系方式必须最小化公开，并在服务端落实访问权限。
- 工作区现有未提交代码均视为用户有效改动，不清理、不重置、不覆盖、不混入无关提交。
- 未经当前对话明确授权，不执行数据库变更、部署或生产环境操作。

## 10. 推荐实施顺序

### 阶段一：确认产品细节与现有能力

1. 确认甄客言首版字段、媒体规则、身份标签选项和审核方式。
2. 检查现有登录、用户、上传、地图、内容、分享和管理端能力。
3. 明确首页首版信息架构和移动端优先的页面结构。
4. 明确地点来源、腾讯地图能力、坐标体系和用户隐私提示。

### 阶段二：地点与甄客言最小闭环

1. 建立统一地点模型或在现有可信模型上补齐地点能力。
2. 完成甄客言后端模型、接口、审核状态和管理入口。
3. 完成甄客言列表、详情、发布、地点选择和身份标签选择。
4. 验证登录回跳、定位失败降级、发布审核、下架和旧链接状态。

### 阶段三：首页与平台心智

1. 将用户默认首页调整为甄客行平台首页。
2. 接入可配置轮播图及安全的内外链跳转。
3. 让甄客言成为首页主体，正常展示本地专区、外地专区等入口，但使用不按定位过滤的冷启动内容池。
4. 将商城调整为辅助入口，保留原有完整业务链路。

### 阶段四：持续扩展

- 根据真实使用情况增加评论、点赞、收藏、关注、评分、搜索和附近内容。
- 当内容量和城市覆盖达到另行确认的门槛后，再将本地专区与用户当前城市或手选城市关联。
- 根据业务优先级深化酒店、饭店、景区等实体详情与交易能力。
- 在内容和交易关系稳定后再讨论推荐算法、商业化和跨城市运营。
- 多租户最后实施，不为远期设想提前建设空表、空接口和通用框架。

## 11. 开发前仍需确认的关键问题

在开始大规模改代码前，至少需要继续确认以下产品细节：

1. 甄客言首版允许纯文字、图片和视频中的哪些形式，各自数量与大小限制是什么。
2. 甄客言是否需要星级或分项评分，还是首版只做帖子内容。
3. 用户视角身份标签的正式选项，以及每篇单独选择还是保存默认值。
4. 帖子公开展示地点名称和地址到什么精度，是否显示用户与地点的距离。
5. 新地点由谁创建、是否需要审核，以及地点重复、纠错和商家认领如何处理。
6. 甄客言首版是否包含点赞、评论、收藏、关注、举报和分享，各自优先级如何。
7. 内容采用先发后审、先审后发，还是机器审核与人工复核结合。
8. 首页除轮播图和甄客言外，第一版确定保留哪些入口和栏目。
9. 外部项目链接允许哪些域名、在微信和普通浏览器中分别如何打开。
10. 第一版本地专区与外地专区是共用平台内容池，还是采用人工运营的非地理内容分区。

当前需求的默认结论是：**立即启动甄客行平台首页与甄客言主线设计；首页左上角必须真实定位并显示当前市区；本地专区、外地专区第一版正常展示但不与设备定位或帖子城市关联，统一采用冷启动内容策略；用户发布甄客言时需要登录、选择地点和视角身份；商城完整保留但降为辅助模块；其他项目可以通过轮播外链导流，但不自动成为甄客行内部业务。**
