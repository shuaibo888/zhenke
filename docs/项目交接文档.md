> 更新时间：2026-08-04
>
> 当前项目是一个完整可用的小型甄客商城。现有功能是后续开发的稳定基线，不再作为“待完成任务”重复实现；新需求统一按功能扩展处理。

## 1. 项目定位

甄客商城不是普通商品货架，而是以“甄客验”为核心的内容电商项目：

```text
试用招募或真实购买
-> 用户获得对应报告资格
-> 用户自愿发布甄客验
-> 甄客验进入首页内容流
-> 其他用户从甄客验进入商品并完成购买
```

现有项目已经形成完整业务闭环，主要包括：

- 商城账号、用户资料、头像和收货地址。
- 商家入驻、平台审核、商品和固定分类管理。
- 线上试用、线下试用、申请审核和分轮招募。
- 试用甄客验、购买评价甄客验、评论、回复和“认为有用”。
- 首页内容流、分类过滤、全局搜索和商品详情。
- 服务端购物车、立即购买、结算、定向优惠券和订单拆分。
- 微信内 JSAPI 支付、订单取消、退款、商家履约和实时物流。
- 用户端、商家端和平台管理端对应的真实业务页面。

所有现有业务都以真实后端 API 和数据库数据为准。禁止用 mock、seed、本地数组、本地计数或前端直接改状态替代真实业务流程。

项目的长期目标是建设可供不同运营主体独立使用的商城 SaaS 中心。当前仍按单租户运行，但从现在开始新增积分、AI 认证、外部登录或其他能力时，都必须避免写死全局唯一主体，并为后续可信租户上下文、数据隔离和租户级配置保留清晰扩展路径。

## 2. 工程结构与入口

当前工作区根目录：`C:\Users\ASUS\Desktop\delivery-main`。代码和配置中不得新增依赖本机目录的绝对路径。

| 模块 | 目录 | 职责 |
|---|---|---|
| 后端 | `delivery-backend` | Spring Boot 3、Java 17、MyBatis、MySQL、Redis |
| 商城业务 | `delivery-backend/ruoyi-shop` | 商城领域、状态流转和业务接口 |
| 启动模块 | `delivery-backend/ruoyi-admin` | 主应用配置、打包和启动 |

继续维护模块化单体，不恢复旧 `ruoyi-ui`，不拆微服务。

### 2.1 后端入口

商城模块按以下层次组织：

```text
controller -> service -> mapper/XML -> domain/dto/vo
```

- Controller 负责接口和基本参数接收。
- Service 负责登录身份、事务、业务资格和状态机。
- Mapper SQL 负责数据归属、期望原状态和并发条件。
- 前端传入的用户、商家、价格、库存、作者和目标状态均不可信。

健康检查为 `GET /health`，经统一网关访问时为 `GET /api/health`。

当前用户端已经按页面和复用组件拆分，主要入口为：

### 2.5 商品图片与详情页基线

2026-08-04 已将商品详情从文字介绍改为纯图片展示，后续不能恢复资源地址输入框或用前端本地地址替代真实上传：

- 商家端商品表单只提供上传组件：封面 1 张、商品主图最多 6 张、详情图最多 6 张；不展示上传后的 URL，也不允许手工填写 URL。
- 商品图片只支持 JPG/PNG，单张不超过 5MB，不再按封面、主图或详情图设置宽高硬限制；普通图片和长图都允许上传，由用户端和商家端通过自适应样式展示。
- 文件类型和大小在前端做即时提示；后端 `ShopProductImageResourceService` 再校验大小、文件扩展名、真实图片格式及二者一致性，但不按像素尺寸拒绝图片。商家端上传接口为 `POST /shop/merchant/products/images`。
- 上传目录按 `product/merchant-{merchantId}` 分区；图片归属仍通过商品和当前商家校验，不能信任前端提交的商家 ID。
- 用户详情页把封面与主图组成自动轮播画廊：默认每 4 秒切换，支持左右按钮、圆点、缩略图和移动端左右滑动；详情图按商家排序纵向展示并使用懒加载，商品列表不查询图片集合，避免增加列表查询开销。
- 商品详情图与“甄客验”使用同一内容面板顶部的左右双标签切换，默认选中“商品详情”；切到“甄客验”后直接展示报告列表，不再使用折叠面板。甄客验接口每页 5 条，首屏只请求第一页，继续下滑时通过滚动哨兵请求下一页，并对并发请求和重复数据做保护，不能退回一次性全量加载。
- 商品存在试用活动时，“申请试用”入口必须铺满商品详情内容区整行，不沿用详情页普通直系按钮的内容宽度规则；移动端继续保留图标、说明和“选择方式”的紧凑分层。
- `shop_product_image.image_type` 明确区分 `MAIN / DETAIL`，同一类型内部使用 `image_sort` 排序；不新增 SKU 表，也不新增另一张详情图表。
- 当前图片表通过 `product_id` 外键继承商品的商家归属；未来多租户化时在商品主表和图片唯一约束中补充 `tenant_id`，上传目录在商家分区外再增加租户分区。

### 2.6 用户端页面刷新基线

用户端不使用 WebSocket，但有状态变化可能由商家端或支付回调产生，因此不能只依赖登录后加载一次的全局缓存：

- 登录恢复后只主动刷新全局需要展示数量的购物车，不再一次并发加载订单、试用、甄客验、地址和优惠券。
- 每次进入 `/profile` 都刷新订单、试用、甄客验和优惠券概览；进入 `/profile/orders`、`/profile/trials`、`/profile/reports`、`/profile/coupons` 时，只刷新当前页面对应数据。
- 打开购物车、打开地址管理和进入结算页时分别刷新当前操作需要的购物车、地址和优惠券数据；商品详情会刷新当前用户的试用申请，避免重复申请判断使用旧状态。
- `useRefreshOnRoute` 同时兼容正常路由卸载和页面缓存场景；从其他页面返回后再次进入目标路由，必须重新请求服务端。
- `ShopContext` 为购物车、订单、试用、甄客验、地址和优惠券分别维护加载状态，同一资源已有请求进行中时复用该 Promise，避免快速切换页面造成重复请求。
- 请求返回前会核对当前登录用户，旧账号未完成的请求不能覆盖新账号数据；页面可以保留旧列表并显示局部加载状态，响应后再替换为服务端最新结果。

## 3. 固定业务规则

### 3.1 身份与数据归属

- 商城用户保存在 `shop_user`；管理员和商家后台账号保存在 `sys_user`。
- 商家是独立经营主体，不是商城会员等级。
- 商城用户 ID 从当前商城登录态获取，商家 ID 从当前后台账号解析。
- 用户地址、购物车、订单和报告资格必须按当前用户在 SQL 中隔离。
- 商家商品、试用、申请、订单和甄客验必须按当前商家在 SQL 中隔离。
- 归属校验不能只写在 Java 中；详情、修改和状态转换 SQL 必须同时带归属条件。
- 状态转换必须使用“资源归属 + 期望原状态”的条件更新，不能先查询后无条件覆盖。

### 3.2 三类甄客验

```text
线上试用：商品上架 -> 招募 -> 用户申请 -> 商家审核 -> 商家发货
         -> 用户确认收货 -> 用户可选发布甄客验

线下试用：商品上架 -> 招募 -> 用户申请 -> 商家审核
         -> 用户可选发布甄客验

购买评价：用户从甄客验或商品进入结算 -> 支付 -> 商家发货
         -> 用户确认收货 -> 按订单项可选发布甄客验
```

- 报告发布始终是可选行为。
- 对外统一称“甄客验”，通过 `reportSource` 区分 `TRIAL / PURCHASE`。
- `TRIAL` 再通过试用类型区分 `ONLINE / OFFLINE`。
- 同一商品的线上和线下试用是两条独立活动，名额、申请和状态互不影响。
- 一个试用申请最多生成一篇有效甄客验。
- 购买评价资格必须绑定当前用户自己的 `RECEIVED` 订单项。
- 一个订单项最多生成一篇有效购买评价；多商品订单按订单项分别发布。
- 查询甄客验时必须兼容购买评价没有试用申请的情况，不能把购买评价强行建模成试用报告。

### 3.3 状态机

```text
商品：DRAFT / ON_SALE / OFF_SALE
试用活动：DRAFT / RECRUITING / CLOSED / FINISHED
试用申请：APPLIED / APPROVED / REJECTED / SHIPPED / RECEIVED / COMPLETED / EXPIRED
订单：PENDING_PAYMENT / PAID / SHIPPED / RECEIVED / CANCELLED / REFUNDING / REFUNDED
```

修改状态枚举或流转前，必须同时阅读对应 Service 事务和 Mapper XML 条件更新。

### 3.4 商品、试用和首页

- 固定分类编码为 `CATEGORY_1` 至 `CATEGORY_4`；名称、排序和启停读取数据库。
- 首页主体是招募中的试用和已发布甄客验，不是普通商品列表。
- 首页内容类型和商品分类过滤由 `/shop/home/feed` 服务端完成。
- 全局搜索使用 `/shop/home/search`，属于独立搜索模式。
- 试用截止按自然日处理，截止当天仍可申请。
- 新一轮试用只应被仍在招募、未截止且未满员的同类型活动阻塞。
- 商品销量按有效订单项汇总，不依赖未维护的前端或静态计数。

### 3.5 购物车、订单和来源归因

- 收货地址每个用户最多 20 个；第一个自动设为默认，删除默认地址后自动补位。
- 服务端购物车按用户隔离，单商品数量限制为 1–99。
- 加购、改数量和结算时重新校验商品状态与库存。
- 创建订单时，后端重新读取并锁定商品，计算真实价格、库存和商家。
- 同商家商品合单，多商家商品拆单；任一条件扣库存失败时整笔回滚。
- 商品、价格、封面和地址等订单关键内容保存快照。
- 购买来源只允许传 `sourceReportId`；后端验证来源甄客验已发布且商品一致后，才写入购物车和订单项。
- 不接收前端传入的来源作者、推广人、商家、价格、优惠金额或结算金额。

### 3.6 优惠券

- 优惠券由平台管理员创建和下发，商家没有创建或下发权限。
- 每张优惠券绑定一个或多个有效商家，不存在平台通用券。
- 用户持券以逐张券记录和唯一券码为准，不能只在前端维护数量。
- 单商家结算可以选择适用优惠券；多商家购物车按原价拆单，不跨商家使用优惠券。
- 创建订单时由后端锁定并校验用户券、有效期、上下架、门槛、用户归属和商家范围，然后原子核销。
- 待付款订单取消或超时取消时返还优惠券；已支付订单退款当前不返券。

### 3.7 支付、退款和物流

- 用户端只允许在微信内置浏览器打开，当前支付方式为微信 JSAPI；H5 支付关闭。
- 支付成功只能由验签通知或后端主动查单确认，不能相信前端回跳参数或支付弹窗结果。
- 支付回调必须保留原始请求体和 `Wechatpay-*` 请求头完成验签。
- 待付款订单取消时先处理支付渠道关单，再更新本地状态和恢复库存。
- 待发货订单申请退款后进入 `REFUNDING`；已发货订单需先完成收货；已收货退款由商家按归属审核。
- 只有可信支付渠道确认退款成功后，订单才进入 `REFUNDED` 并按既定规则恢复库存。
- 平台管理员订单能力保持全局只读，不复用商家发货或退款审核接口。
- 平台履约事件与第三方实时物流轨迹分开展示；物流查询只使用服务端订单中的运单号。
- 前端不得展示第三方物流供应商名称，也不得直接透传供应商原始错误信息。

### 3.8 评论与“认为有用”

- 评论作者身份只取当前登录态，前端不能传入评论用户 ID。
- “作者”标识由评论用户与甄客验作者的真实 ID 关系计算，不能比较昵称。
- 评论删除为软删除；删除一级评论时，其回复也必须从正常查询中消失。
- “认为有用”依赖数据库唯一约束，同一用户对同一甄客验最多一条有效记录。
- 甄客验作者不能给自己的内容标记有用。
- 公开甄客验允许匿名查看；登录用户查看时可返回其真实 `usefulByMe` 状态。

## 5. 重点回归风险

- PageHelper 列表必须先解析当前商家，再 `startPage()`，最后执行列表查询。
- 未知接口列表先用 `Array.isArray` 归一化，不能直接 `.map()`。
- 图片和视频 URL 使用独立 React 状态，不能把 Upload 事件对象直接保存为业务字段。
- 验证码继续保留加载成功、加载中和加载失败状态；按钮回调使用显式包装函数。
- 管理端订单接口必须根据当前登录类型区分平台管理员与商家。
- 商家名称和甄客验类型优先使用服务端 DTO 返回值，不能在前端猜测或用其他列表反查。
- 商家甄客验必须使用按当前商家归属过滤的真实接口，不能恢复 `seedReports` 或本地上下架。
- 退款、取消、支付、收货和发货都必须保留“归属 + 期望原状态”的条件更新。
- 线上试用不能绕过收货发布报告，线下试用不能进入物流流程。
- 购买评价必须按 `orderItemId` 校验，不能按整张订单或 `productId` 去重。
- 来源归因只信任服务端验证后的 `sourceReportId`。
- 前端 Modal/Drawer 打开时必须锁定底层页面，长内容在弹层内部滚动。
- API 私钥、APIv3 密钥、AppSecret、OAuth state 密钥和其他凭据不得提交 Git、写入日志或返回前端。

## 6. 现有模块基线与后续方向

后续扩展顺序为：

1. 先按 §6.2 建设最简单的商城积分系统，这是当前最高优先级任务。
2. 积分系统完成后，再按 §6.3 开发商品 AI 智能认证。
3. 商品 AI 智能认证完成后，再与外部赛事软件开发人员对接 §6.4 的单点登录和后续积分能力。
4. 正式多租户基础、甄客验智能评分和其他能力继续作为更后续的独立扩展；多租户 SaaS 同时是当前所有新功能必须遵守的长期设计约束。

这些能力都建立在当前完整可用项目之上，不属于当前基础业务缺陷。

### 6.1 普通商城模块基线

#### 6.1.1 最终产品边界

普通商城提供基础分类浏览、多字段搜索和真实商品入口，不建设 SKU、SPU、品牌库、二级分类、复杂筛选、排序、促销横幅或推荐系统。

- 一个 `shop_product` 就是一种可以直接购买的商品，继续使用一组价格和库存。
- 容量、颜色、包装等规格不同且价格或库存需要独立管理时，商家重新创建一条商品。
- 商品名必须包含完整规格，例如“矿泉水 550ml×24瓶”；不能只把关键规格写在副标题中，因为订单项保存的是商品名称快照。
- `shop_product` 增加商家自行填写的 `brand_name` 文本字段；不新增品牌表或平台品牌库。
- 没有新增 `shop_product_sku` 或分类字段，购物车和订单仍以 `productId` 为交易商品单位。
- 现有四个固定分类继续作为基础分类；平台管理员维护名称、排序和启停，商家只选择有效分类。

#### 6.1.2 用户端页面

用户端新增 `/mall`，固定布局为：

```text
顶部：商城多字段搜索
主体：左侧分类导航 | 右侧商品列表
底部：首页 | 商城 | 我的
```

- 搜索支持商品名、副标题、商家填写的品牌、商家名称、分类名称和商品编号；不对商品详情大文本做 `%LIKE%` 扫描。
- 搜索由 MySQL 服务端分页完成，不能先获取全部商品再由前端过滤；关键词最长 50 个字符。
- 搜索只在用户提交或清空时请求，不随每次键盘输入发请求；搜索框使用轻量的内嵌图标、清空按钮和搜索按钮。
- 搜索与当前左侧分类组合生效，清空关键词后返回当前分类的普通商品列表。
- 左侧包含“全部商品”和服务端返回的启用分类，按 `categoryId` 筛选，不依赖中文名称。
- 切换分类时右侧清空旧结果并从第一页重新加载；快速切换通过请求版本隔离，旧请求不能覆盖新分类。
- 右侧展示商品主图、品牌、完整商品名、副标题、价格、真实销量、商家和售罄状态；品牌标签与商品名在首行排列，商品名仍是视觉主体。
- 当前分类无商品时展示明确空状态，不混入其他分类商品。
- 点击商品进入现有 `/products/{productId}` 详情页；详情主信息同样把品牌标签放在商品标题前，并继续复用真实购物车、结算、优惠券、订单、支付、退款和物流。
- 第一阶段不在列表卡片中增加快捷加购，避免复制商品详情中的交易逻辑。
- 三项导航在 `/mall` 刷新后仍保持商城选中，移动端继续使用底部安全区；悬浮购物车继续访问同一份服务端购物车。

主要入口：

```text

delivery-frontend/src/components/AppChrome.tsx
delivery-frontend/src/services/shopContent.ts
delivery-frontend/src/styles/commerce.less
delivery-frontend/.umirc.ts
```

#### 6.1.3 后端公开商品接口

新增真实分页接口：

```text
GET /shop/mall/products?categoryId=&keyword=&pageNum=&pageSize=
```

- 默认每页 12 条，服务端单次硬限制最多 24 条。
- 只返回 `ON_SALE`、未删除、分类已启用、所属商家已审核且启用的商品。
- 分类和关键词条件都在 Mapper SQL 中完成；关键词覆盖商品名、副标题、品牌、商家、分类和商品编号。
- 第一页执行 `count` 并返回真实总数，后续“加载更多”页关闭重复 `count`；前端保留第一页总数，不使用后续页的 `total` 字段覆盖。
- 全部在售列表和按分类在售列表分别使用联合索引；图片继续使用浏览器懒加载，列表不会一次获取全量商品。
- 库存为零的在售商品仍可展示为“已售罄”，商品详情和下单服务继续阻止无库存购买。
- 分类继续复用 `GET /shop/products/categories`，详情继续复用 `GET /shop/products/{productId}`。

主要入口：

```text

delivery-backend/ruoyi-shop/src/main/java/com/ruoyi/shop/service/ShopProductService.java
delivery-backend/ruoyi-shop/src/main/java/com/ruoyi/shop/mapper/ShopProductMapper.java
delivery-backend/ruoyi-shop/src/main/resources/mapper/shop/ShopProductMapper.xml
```

#### 6.1.4 商家操作

- 商家继续使用现有商品表单，填写分类、品牌、完整商品名、副标题、封面、主图、详情图、价格和库存；商品详情不再提供文字介绍。
- 品牌为必填自由文本，最长 100 个字符；没有品牌时由商家明确填写“无品牌”。
- 商品名表单保留“请包含规格”的说明和示例，不增加规格编辑器。
- 分类设置入口只对具有分类编辑权限的平台管理员显示，商家只能选择启用分类。
- 商家商品查询、编辑和上下架继续使用现有 `merchantId + productId` 服务端归属校验。

#### 6.1.5 库存和交易链路

普通商城没有修改库存扣减、购物车或订单结构：

- 现有下单事务会按 `productId` 重新读取服务端商品、价格、库存和商家。
- 商品查询使用 `for update` 行锁，扣减使用 `stock >= quantity` 条件更新。
- 任一商品库存不足时创建订单失败并回滚；取消和既定退款流程继续按现有规则恢复库存。
- 普通商城只提供商品发现入口，不能新增绕过 `ShopOrderService` 的下单或扣库存路径。

#### 6.1.6 当前单租户与 SaaS 预留

当前项目尚未实现 `tenant_id`、租户上下文或租户解析，本次不得只给商城局部增加租户字段形成伪隔离。

- `merchant_id` 继续表示租户内商家，不能冒充租户 ID。
- 前端和公开接口不接收可篡改的 `tenantId`；未来由域名、登录令牌或其他可信入口解析服务端租户上下文。
- 商城商品查询集中在 Service 和 Mapper；未来必须在商品、商家和分类查询中统一追加当前租户条件。
- 分类由后端返回，不在前端写死；未来分类唯一规则建议使用 `tenant_id + category_code`。
- 品牌当前是商品自身字段，未来随商品一起按租户隔离；不得因为品牌文本相同就跨租户关联商品。
- 多租户落地后，商城列表索引必须将可信的 `tenant_id` 放在联合索引前缀，并同步把租户条件加入 Mapper，不能继续依赖当前单租户索引。
- 新增租户归属表时必须同时考虑租户字段、联合唯一约束、索引、Mapper 条件、缓存 Key、上传目录和审计日志。
- 正式多租户改造必须覆盖用户、商家、分类、商品、购物车、订单、甄客验、试用、优惠券、支付配置和文件存储，不能只修改商城列表。

### 6.2 商城积分系统（当前最高优先级）

当前只建设商城自身最基础的积分能力：每个商城用户有一个服务端持久化的积分账户，登录用户可以查看当前积分、累计划入和累计消费。

第一阶段范围：

- 商城不生产积分，不增加签到、下单奖励、活动奖励或其他积分获取规则。
- 暂不对接外部赛事软件，不处理外部积分如何划拨进入商城。
- 暂不支持积分消费、抵扣、冻结、过期、转赠、退款返还、排行榜或运营发放，但需要保留只读的积分变更记录。
- 当前积分、累计划入和累计消费均按非负整数处理；没有积分数据的用户按 `0` 展示。
- 当前积分是商城内可消费余额的权威值，累计划入和累计消费只是统计指标，不能使用“累计划入 - 累计消费”反推或覆盖当前积分。
- 积分归属只根据当前商城登录用户确定，接口不接收可篡改的用户 ID。
- 积分必须保存在服务端并通过真实接口读取，不能使用前端常量、本地缓存或模拟数据。
- 用户端在个人资料卡右侧紧凑展示当前积分，不在“我的服务”中单独占用模块卡片。
- 点击积分展示进入只读积分明细页；页面顶部展示当前积分、累计划入和累计消费，记录按时间倒序展示变更原因、本次增加或减少的积分、变更后余额和变更时间，并使用服务端分页。
- 当前没有积分写入来源时记录列表允许为空，不为演示效果生成本地假记录。
- 本阶段不改变商品价格、购物车、结算、优惠券、订单、支付和退款流程。
- 积分账户不能按“全平台只有一个运营主体”的假设设计；数据访问集中在 Service 和 Mapper，正式多租户后积分唯一归属应自然扩展为 `tenant_id + shop_user_id`。
- 当前尚无可信租户上下文，因此本阶段不接收前端 `tenantId`，也不为积分功能单独添加默认租户或局部伪隔离。

第一阶段验收标准：

1. 每个商城用户都有独立积分账户，用户只能查看自己的当前积分、累计划入、累计消费和积分明细。
2. 刷新页面或重新登录后，积分仍以服务端保存的数据为准。
3. 用户无法通过修改请求参数读取或修改其他用户积分。
4. 个人资料卡能直接看到积分余额，点击后可以查看只属于当前用户的积分变更记录。
5. 页面不存在手工增加、扣减、消费或外部同步入口，空记录使用真实空状态。

后续外部积分对接和商城消费必须遵守以下一致性规则：

- 外部赛事系统负责生产积分并保存用户历史总积分、尚未划出的当前积分和划拨记录；商城不生产积分。
- 用户完成外部身份绑定后，积分通过划拨进入商城。划拨成功时，上游当前积分减少（全量划拨时归零），商城当前积分与累计划入同步增加；划入后的积分由商城负责消费、退款和冲正。
- 商城消费已经划入的积分时，只操作商城积分账户，不再实时调用上游系统；商城是已划入积分余额及商城消费流水的权威方。
- 每次划拨必须具有稳定且唯一的划拨单号；商城按“租户 + 来源系统 + 外部划拨单号”幂等入账，重复通知不得重复增加积分。
- 上游不能采用“先清零后单次通知”的无补偿流程。应先生成划拨单并扣减或冻结待划拨积分，商城幂等入账成功后双方确认成功；超时可重试或查询，失败可补偿，不能让积分丢失或重复。
- 只有已确认成功的变更进入用户可见流水和累计统计；退款、撤销、冲正必须保存独立反向流水，不能直接删除或改写历史成功记录。
- 需要保留来源系统、外部划拨单号、业务类型、业务编号、处理状态和最后划入时间，并提供定期对账与异常补偿能力。
- 商城“累计划入”只统计已经确认成功的划拨金额，不等同于上游系统记录的用户历史总积分。
- 正式多租户后，积分账户、流水、幂等键、划拨任务和对账任务都必须带可信 `tenant_id`，且租户身份只能由服务端上下文确定。

当前源码已包含只读查询接口、个人资料卡积分入口和积分明细页；建表脚本已经执行并由用户删除，后续需完成后端运行与页面验收。

### 6.3 商品 AI 智能认证（积分系统之后实现）

#### 6.3.1 甲方确认的产品定义

- 商家可以对自己上传的商品发起 AI 智能认证申请。
- 商家按当前商品提交品牌、供货来源、生产或采购信息、证明材料和商品照片。
- 平台调用 AI 大模型识别并验证材料；AI 认为材料能够证实当前商品真实、权威且与商品相符时，认证通过。
- 认证通过的商品向消费者展示明显的“平台 AI 智能验证”标识和认证摘要。
- 标识证明的是：该商品已经通过平台 AI 基于商家提交材料进行的智能验证。
- 商家必须承诺全部信息和材料真实、有效，并对虚假、伪造、隐瞒或误导性提交承担责任。
- 按甲方确定的产品处理口径，若商家提交虚假信息但被 AI 认证通过，相关商品真实性纠纷由消费者与商家依法处理，可通过互联网法院等合法渠道解决；平台不参与双方商品真实性争议处理。
- 页面和提交协议必须明确：AI 认证结论以商家提交材料为基础，平台不对商家材料本身未被发现的造假承担保证责任。

消费者端建议统一说明：

> 该商品已通过平台 AI 智能验证。验证结论基于商家提交的商品及相关证明材料；商家对材料的真实性、完整性和有效性负责。若存在虚假、伪造或隐瞒，由商家承担相应责任，相关争议由消费者与商家依法处理。

具体标识名称、图标和最终协议文案可在实现页面时确认，但不得在同一页面出现相互矛盾的责任说明。

#### 6.3.2 商家入口与状态

商家商品管理列表在“编辑商品、上下架、发布试用”旁增加“申请 AI 认证”入口，只能操作当前商家自己的商品。

认证状态独立于商品上下架状态：

```text
NOT_APPLIED  未申请
DRAFT        填写中
SUBMITTED    已提交
AI_REVIEWING AI验证中
NEED_MORE    待补充
PASSED       认证通过
REJECTED     认证未通过
EXPIRED      已失效
```

- 同一商品同一时间只能有一份当前申请，重复提交必须幂等。
- `NEED_MORE / REJECTED / EXPIRED` 可以修改材料后重新提交。
- AI 服务异常时保持待处理或重试状态，不能默认通过，也不能影响商品原有销售状态。
- 商品名称、品牌、分类、型号、条形码或主要包装等认证关键内容发生变化后，原认证失效并要求重新申请。
- 价格和库存变化不影响认证结果。

#### 6.3.3 第一阶段商家提交内容

第一阶段采用少量必填加按来源动态出现的补充项，不直接照搬参考表单。基础必填内容为：

1. 商品来源：品牌方直接供货、品牌授权经销、供应商采购、自有品牌、自有生产或其他来源。
2. 商品品牌，或者明确选择无品牌。
3. 商品产地和实际发货地。
4. 供货方、品牌持有人或生产主体名称。
5. 当前商品与材料的对应依据，至少包含商品名称、品牌、型号、货号、条形码、SKU、批次号或包装标签中的一项。
6. 至少一份供货或生产证明材料。
7. 当前实际销售商品的正面照片。
8. 商品包装、标签、条形码或生产信息照片。
9. 商家真实性声明和 AI 处理授权确认。

材料类型包括：

- 品牌授权书、经销或代理证明。
- 采购合同、供货协议、采购发票、采购订单、送货单或入库单。
- 自有品牌证明、生产证明或委托生产证明。
- 其他能够说明商品来源和商品对应关系的材料。

图片和 PDF 作为第一阶段主要文件类型。合同价格、银行账号等与认证无关的内容允许商家预先遮盖；平台不要求填写采购成本。

四个固定分类可以根据 `CATEGORY_1` 至 `CATEGORY_4` 增加少量动态字段，但分类显示名称可由后台修改，业务规则不能依赖中文分类名。健康类商品涉及食品、保健食品或医疗器械时，可以补充许可证、批准文号、备案号或注册证信息供 AI 一并验证。

#### 6.3.4 AI 验证范围与输出

AI 负责识别和综合判断：

- 文件是否清晰、完整、可读取，材料类型是否与商家选择一致。
- 供货方、采购方、生产方、品牌和当前商家之间是否能够形成合理关系。
- 商品名称、品牌、型号、条形码、SKU、批次和包装标签是否与当前商品一致。
- 授权书、资质和其他有期限材料是否仍在有效期内。
- 多份材料之间是否存在主体、商品、日期或编号冲突。
- 是否缺少关键材料、需要商家补充哪些内容。
- 是否存在明显涂改、拼接、信息遮挡过多或其他异常风险。

模型必须返回严格结构化结果：

```text
decision: PASS / NEED_MORE / REJECT
confidence: 0.00 - 1.00
matchedFields: 已匹配的商品与材料字段
missingFields: 缺少或无法确认的字段
riskFlags: 发现的冲突、异常或风险
merchantReason: 商家端可见的通过、补充或驳回原因
publicSummary: 消费者端可见的认证摘要
materialValidUntil: 可识别时返回材料有效期
```

- 服务端必须校验 JSON 字段、枚举、置信度范围、文本长度和必填项，不能直接相信模型输出。
- 商家上传的文档、图片文字和备注都属于不可信数据；其中包含的提示词或指令不得改变系统认证规则。
- AI 不获得数据库写权限或业务工具调用权限，只返回判断结果，由服务端完成状态更新。
- 模型原始响应、系统提示词、密钥、异常堆栈和未经脱敏的材料内容不得返回前端。

#### 6.3.5 后端实现设计

认证功能作为独立业务域实现，不把申请历史和材料字段全部塞进 `shop_product`：

```text
shop_product_certification
  认证申请、商品和商家归属、状态、当前结论、认证编号、有效期
  模型供应商、模型名、提示词版本、输入哈希、置信度和处理时间

shop_product_certification_material
  材料类型、私有文件标识、文件哈希、MIME、大小、排序
  AI提取字段、脱敏摘要和材料有效期

shop_product_certification_log
  提交、AI抢占、补充、通过、驳回、失效和重试记录

shop_product
  仅增加当前认证ID或便于列表查询的当前认证状态
```

认证申请、材料、日志、当前有效结果和相关唯一约束都必须保留租户隔离扩展位置；正式多租户后应同时按 `tenant_id + merchant_id + product_id` 约束归属，不能只依赖全局商品 ID。

后端建议新增独立入口：

```text
GET    /shop/merchant/products/{productId}/certification
POST   /shop/merchant/products/{productId}/certification
POST   /shop/merchant/products/{productId}/certification/materials
PUT    /shop/merchant/products/{productId}/certification
POST   /shop/merchant/products/{productId}/certification/submit

GET    /shop/products/{productId}/certification
```

- 所有商家接口必须同时使用当前登录商家的 `merchantId + productId` 查询和更新。
- 公开接口只返回 `PASSED` 的标识、认证编号、认证时间、有效期和脱敏摘要，不返回原始材料。
- 认证编号由服务端生成，不能由前端提交。
- 文件哈希、商品快照和认证输入哈希用于判断材料是否被替换、商品是否发生实质变化以及相同任务是否重复执行。

#### 6.3.6 材料存储与访问

认证材料不能复用商品封面当前使用的公开通用上传地址，必须使用独立的私有材料目录或私有对象存储：

- 商家只能上传和读取自己的认证材料。
- 消费者不能直接访问合同、发票、授权书等原始文件。
- 校验文件扩展名、真实 MIME、文件头、大小、图片尺寸和 PDF 页数。
- 保存文件 SHA-256，提交后禁止静默替换原文件。
- 文件名、日志和异常信息不能泄露证件号、银行账号、联系人等材料内容。
- 消费者端只展示 AI 生成并经服务端过滤的认证摘要。

#### 6.3.7 异步任务与模型配置

复用现有甄客验智能评分的“持久化任务、条件抢占、事务外调用、失败重试、应用重启恢复”思路，但使用独立的认证 Service、Mapper、任务表和配置，不能复用报告评分记录。

```text
商家提交并固化商品/材料快照
-> 创建 SUBMITTED 任务
-> 调度器条件抢占为 AI_REVIEWING
-> 图片/PDF内容识别和结构化字段提取
-> AI综合判断并返回严格JSON
-> 服务端校验并持久化审计记录
-> PASSED / NEED_MORE / REJECTED
-> PASSED 商品对消费者展示认证标识
```

- 新增独立 `shop.product-certification` 配置段和功能开关。
- 当前甄客验评分模型以文本输入为主；商品认证需要选择支持图片和文档理解的多模态模型，并在实现时验证 Spring AI Alibaba 适配能力。
- 模型超时、限流、解析失败和应用重启不能丢失申请，也不能产生多个当前有效结果。
- 按商家和商品限制提交频率与并发任务数，避免重复上传消耗模型额度。

#### 6.3.8 前端展示

商家端：

- 商品列表增加认证状态和“申请/查看 AI 认证”操作。
- 认证抽屉或独立页面展示当前商品、动态表单、材料上传、真实性声明和提交按钮。
- 提交后展示 AI 验证进度、通过摘要、待补充内容或未通过原因。

消费者端：

- 首页商品相关区域和商品详情根据后端 `PASSED` 状态展示统一认证标识。
- 点击标识展示认证编号、认证时间、有效期、材料类型摘要、匹配依据和责任说明。
- 不展示完整合同、发票、授权书、证照原图或模型原始响应。
- 认证未通过、待补充、处理中或已失效时不展示通过标识。

#### 6.3.9 验收标准

1. 商家只能为自己的商品申请认证，无法读取或修改其他商家的申请和材料。
2. 一份申请可以上传图片和 PDF，材料保持私有，消费者无法直接访问原文件。
3. AI 任务异步执行；超时、限流、非法 JSON 和应用重启不会误标通过或丢失申请。
4. `PASS / NEED_MORE / REJECT` 均保存模型、提示词版本、输入哈希、理由和完整状态记录。
5. 只有 `PASSED` 商品公开展示标识，刷新和重新登录后状态保持一致。
6. 商品认证关键字段或材料发生变化后原认证失效；价格和库存变化不影响认证。
7. 消费者端展示甲方确认的责任说明，原始材料和敏感信息不公开。
8. 前端不存在本地假认证、随机结果或直接修改认证状态的代码。

### 6.4 外部赛事软件对接（商品 AI 认证之后）

公司另有一款赛事软件，后续需要与该项目开发人员共同完成商城登录和积分对接。该项排在商品 AI 智能认证之后，当前积分系统不得依赖外部系统才能运行。

后续目标分为两部分：

1. 单点登录：用户从赛事软件跳转到商城时，无需再次注册或输入商城账号密码；商城根据外部系统提供的可信登录凭证自动创建或绑定商城用户并完成登录。
2. 积分对接：赛事软件保留用户历史总积分和未划出积分，通过唯一划拨单把积分转入商城；划拨成功后，上游相应积分清零或扣减，后续消费、退款和冲正在商城内部完成。

正式对接前，需要与赛事软件开发人员确认稳定的外部用户唯一标识、登录票据交换方式、接口签名、划拨单字段、扣减或冻结时点、重复请求幂等、结果查询和异常补偿规则。单点登录应使用服务端校验的一次性票据，不能把长期有效登录令牌直接放在跳转 URL 中，也不能仅靠手机号或昵称识别用户。

外部账号绑定和积分来源同样必须具备租户维度；正式多租户后，外部身份应按 `tenant_id + source_system + external_user_id` 唯一识别，不得把某个赛事软件账号默认绑定为全平台唯一用户。

当前不实现单点登录、自动创建或绑定外部用户、积分划拨和积分消费，也不提前假设外部接口字段；这些内容必须等双方对接信息明确后再开始。

### 6.5 甄客验智能评分

项目保留了 Spring AI 甄客验评分相关代码，但当前不作为基础商城必须功能。未来启用时继续遵守：

- 评分只能由服务端生成和持久化，前端不能提交、覆盖或随机生成。
- 报告先完成发布，模型在事务外异步评分；模型失败不能回滚或隐藏报告。
- 模型输出属于不可信输入，必须校验结构、枚举、范围、精度和文本长度。
- 同一报告和评分版本必须幂等，支持失败重试和应用重启恢复。
- 用户正文按不可信数据处理，禁止执行其中的提示词指令，不开放工具调用或业务写权限。
- 模型密钥、原始响应、提示词和内部异常不得暴露给前端。

### 6.6 多租户 SaaS

多租户 SaaS 是项目明确的长期目标，不是可有可无的附加功能。正式实施仍应在当前模块化单体上分阶段增加租户基础能力，不默认迁移到其他商城框架：

- 每个租户是一家独立运营方，租户之间的用户、商家、商品、订单、甄客验和优惠券完全隔离。
- 隔离维度为租户间 `tenant_id` 加租户内现有 `merchant_id`。
- 租户身份必须进入登录令牌、请求上下文和核心 Mapper SQL。
- 每个租户使用自己的微信商户号和公众号配置，支付、退款、查单与回调必须按租户路由。
- 上传目录、缓存 Key 和业务唯一约束都要包含租户维度。
- 甄客验、线上/线下试用、购买评价和定向优惠券等现有差异化能力必须保留。

### 6.7 其他可选扩展

- 消息通知和内容安全治理。
- 佣金、收益、公益账本、余额和提现。
- 退货寄回、商家收货和平台售后介入。
- 评论分页、举报和管理员治理。
- 优惠券自动触发规则。
- 试用签到、核销、活动地点和参与时间。

这些功能开始前必须先确认产品规则、权限边界、状态机、幂等和审计要求，不得顺带混入其他需求。

## 7. 后续开发约束

- 所有新功能在设计阶段都必须说明租户归属、可信租户来源、数据隔离位置，以及表结构、唯一约束、索引、缓存 Key、上传目录、配置和审计日志如何加入租户维度。
- 当前没有统一租户上下文时，不接受前端传入的 `tenantId`，不在单个业务里硬编码默认租户，也不局部增加无法形成真实隔离的租户字段。
- 新增查询和状态更新继续集中在 Service 与 Mapper，并保留统一追加当前租户条件的位置；不能把全局唯一、全局配置或跨主体共享数据写死在页面和业务代码中。
- 积分账户、外部身份绑定、AI 模型配置、认证材料、支付配置和文件资源均视为未来租户级资源，当前实现不得阻断以后按租户拆分。
- 用户端保持页面与复用组件拆分，不恢复成单文件承载整站。
- 修改业务前先读对应 Service 和 Mapper XML，确认事务、归属和状态转换。
- 新增能力按后端 DTO、Mapper、Service、Controller、测试、前端 service DTO、页面的纵向切片完成。
- 页面只能接真实 service，不在页面中模拟业务成功。
- 新接口同步处理权限、参数校验、错误信息和前端类型。
- 数据库结构扩展使用新的版本化变更，不重复依赖历史变更记录。
- 未经用户在当前对话明确授权，不恢复依赖，不运行测试、构建、数据库变更或部署。
- 不提交 `.deploy/`、数据库快照、环境变量、密钥、依赖目录和构建产物。
- 工作区存在未提交修改时必须保留，不得擅自清理、重置或覆盖。
