## 1. 项目定位与当前顺序

甄客商城是以“甄客验”为核心的内容电商项目，现有商城、试用、甄客验、购物车、优惠券、订单、支付、退款和履约链路均使用真实后端 API 与数据库数据。

长期目标是把商城建设为支持多运营主体的 SaaS 中心。当前仍是单租户系统，但任何新增功能都不能写死“全平台只有一个主体”，必须为可信租户上下文、数据隔离和租户级配置保留扩展位置。

后续优先级：

1. 先完成本批后台权限、商家优惠券和日期控件的页面验收。
2. 商品平台 AI 认证第一版源码已经完成，下一步是执行迁移、配置并进行接口和页面联调验收。
3. 商品平台 AI 认证验收后，再与外部赛事软件对接单点登录和积分划拨。
4. 多租户 SaaS 是贯穿所有阶段的设计约束，正式改造时间另行确认。

后端继续采用模块化单体：

```text
controller -> service -> mapper/XML -> domain/dto/vo
```

- Controller 负责接口和基本参数接收。
- Service 负责身份解析、事务、业务资格和状态机。
- Mapper SQL 负责数据归属、期望原状态和并发条件。
- 前端传入的用户、商家、租户、价格、库存、作者和目标状态均不可信。
- 页面只能连接真实 Service，不得使用 mock、本地数组或前端直接改状态模拟成功。

## 3. 必须保持的业务规则

### 3.1 身份、权限与数据归属

- 商城用户保存在 `shop_user`；管理员和商家后台账号保存在 `sys_user`。
- 商城用户 ID 取自商城登录态；商家 ID 取自后台登录账号；当前不接受前端传入的 `tenantId`。
- 用户数据必须按当前用户隔离，商家数据必须按当前商家隔离；归属条件同时落实到 Service 和 Mapper SQL。
- 状态更新使用“资源归属 + 期望原状态”条件更新，不能先查询后无条件覆盖。
- 管理员可查看全平台已有商品、试用、申请、订单和甄客验，并可执行商家已有的编辑、上下架、结束招募、审核、发货、核销、物流查询和退款审核操作。
- 管理员不代商家新建商品，也不代商家发布试用。
- 只有管理员可以逻辑删除甄客验；商家只能查看自己商品下的甄客验且无删除权限。逻辑删除保留原始内容、删除人和删除时间。

### 3.2 甄客验与交易

- 对外统一称“甄客验”，`reportSource` 区分 `TRIAL / PURCHASE`，试用再区分 `ONLINE / OFFLINE`。
- 报告发布始终可选；一个试用申请或一个已收货订单项最多生成一篇有效甄客验。
- 创建订单时由后端锁定商品并重新计算真实价格、库存和商家；同商家合单、多商家拆单。
- 购买来源只接受 `sourceReportId`，服务端确认甄客验已发布且商品一致后才记录归因。
- 支付成功只信任验签回调或后端主动查单，不信任前端回跳结果。
- 退款、取消、发货、收货和核销必须保留归属、原状态校验和服务端审计。

### 3.3 优惠券

- 优惠券适用范围分为 `MERCHANT_SPECIFIC`（指定商家）和 `PLATFORM_WIDE`（全平台通用）。历史券保持指定商家类型。
- 管理员可创建指定多个有效商家的优惠券，也可创建全平台通用券；两类券都可以定向下发给多个用户。
- 全平台通用券固定无门槛，服务端强制保存 `minimum_spend = 0.00`，不写入适用商家关联，可用于任一正常营业商家；多商家购物车仍按现有规则拆单，优惠券只允许在单商家结算中使用。
- 单商家订单支持多张券叠加，也支持指定商家券与全平台通用券混合使用。每张商家券的使用门槛按优惠前商品合计判断。
- 券面额允许大于或等于商品金额；总优惠最多抵至商品合计，最低实付为 0 元。0 元订单直接进入 `PAID`、支付渠道记为 `COUPON`，不调用微信支付。
- 订单用券写入 `shop_order_coupon` 多券明细，并记录每张券的券面额与实际抵扣额；旧的 `shop_order.user_coupon_id` 已从模型和迁移中删除。
- 商家可创建、管理并向多个商城用户下发自有优惠券；适用范围由服务端固定为当前商家，商家端不显示商家选择项。
- 商家只能管理自己创建的指定商家券，不能看到或操作全平台通用券、管理员券或其他商家的券。
- 全平台通用券必须设置正整数积分兑换价格；每个用户对同一张通用券最多兑换一次。管理员仍可绕过积分兑换入口直接定向下发。
- 后台只选择开始日期和结束日期，服务端统一归一为开始日 `00:00:00`、结束日 `23:59:59`；同一天有效合法。
- 后台日期控件使用 Ant Design `DatePicker`，占位词为“请选择开始日期 / 请选择结束日期”，日历使用中文月份和中文星期。
- 用户端优惠券有效期分两行展示完整时间：第一行“开始时间 至”，第二行显示结束时间。
- 结算页以多选方式展示优惠券并实时预览优惠与实付；当新增一张券会首次把订单抵到 0 元时必须二次确认，订单已经为 0 元后不允许继续选择多余优惠券。
- 下单时后端锁定并校验用户券、有效期、状态、门槛、用户归属和商家范围后原子核销；待付款订单取消或超时取消返券。

### 3.4 积分系统

积分账户在原只读能力基础上增加了“兑换全平台通用优惠券”这一种受控消费场景：

- 每个商城用户有独立积分账户，可查看当前积分、累计划入、累计消费和分页变更记录。
- “我的积分”页面展示积分余额和可兑换通用券，积分变更记录迁移到 `/profile/point-records` 独立页面，由余额卡片右上角“积分明细”进入。
- 商城不生产积分，当前没有签到、下单奖励、运营发放或手工增减入口。
- 当前只允许积分兑换全平台券，不支持订单金额直接抵扣、冻结、过期、转赠、退款返还或外部自动同步。
- 兑换事务锁定优惠券和当前用户积分账户，在同一事务内完成库存占用、积分扣减、累计消费、积分流水、发券和兑换审计；任一步失败全部回滚。
- 当前积分是商城可消费余额的权威值；累计划入和累计消费仅是统计值，不能反推覆盖余额。
- 积分归属只根据当前登录用户确定，不能从请求中指定其他用户。
- 后续多租户唯一归属应扩展为 `tenant_id + shop_user_id`。

## 5. 已完成源码、待迁移联调：商品平台 AI 认证

### 5.1 产品定义

- 商家可为自己的商品提交品牌、来源、生产或采购信息、证明材料及商品照片，申请 AI 智能认证。
- AI 根据商家提交材料判断材料是否能够证明商品真实、来源合理且与当前商品匹配。
- 第一版完全由 AI 大模型作出通过或未通过结论，不增加管理员人工复核环节。
- 只有认证通过且仍在有效期内的商品向消费者展示“平台AI认证”标识和脱敏摘要；商城列表使用封面右上角的迷你单行角标，详情页展示完整认证信息。
- 商城商品列表中，有效认证商品排在未认证商品之前；同组商品继续按原有商品顺序展示。
- 商家必须承诺材料真实、完整、有效，并承担虚假、伪造、隐瞒或误导性提交的责任。
- 页面固定说明：认证结论基于商家提交材料，平台提供 AI 信息识别和电子存证服务，不代表平台对商品真伪、质量或法律合规作出鉴定或担保。

### 5.2 状态与入口

商家商品列表的操作区增加认证入口，只能操作当前商家的商品。按钮根据状态显示为“申请平台认证 / 查看认证 / 重新申请”，认证状态独立于商品上下架状态：

```text
NOT_APPLIED  未申请
PROCESSING   处理中
PASSED       认证通过
REJECTED     认证未通过
EXPIRED      已失效
```

- 同一商品同一时间只能有一份当前申请，重复提交必须幂等；处理中不能重复提交。
- `REJECTED / EXPIRED` 可以重新申请，表单从上一版服务端记录回填，商家可在原资料和原材料基础上修改后再次提交。
- 未通过必须向商家展示经过安全处理的具体原因，但不得暴露提示词、原始模型响应、密钥或异常堆栈。
- AI 技术异常时继续保持处理中并按持久化任务规则重试，不能默认通过、不能误标为商家材料未通过，也不能影响商品销售状态。
- 商品名称、品牌、分类、型号、条形码或主要包装等关键内容变化后，原认证失效；价格和库存变化不影响认证。
- 认证默认有效 365 天；材料存在更早有效期时取更早日期。

### 5.3 第一阶段材料

第一版保持单页简单表单，基础必填内容：

1. 商品来源：品牌方直接供货、经销商或供应商供货、自有品牌或自有生产、其他来源。
2. 供货方名称：品牌方、供应商或生产企业名称。
3. 商品产地和实际发货地。
4. 商品核对信息：商家选择“包装上的型号或货号、包装条形码、材料中的商品名称、没有编号按包装标签”之一，并填写供货证明或商品包装上能够找到的对应内容。页面使用日常语言说明这是为了核对材料和当前商品是否为同一个商品，不向商家展示内部技术字段。
5. 至少一份供货证明并选择材料类型：品牌授权书、采购合同、采购发票或订单、送货单或入库单、自有生产证明、其他供货材料。
6. 两张商品实拍照片：当前实际销售商品正面照片，以及包装、标签或条形码照片。

提交前只有一个确认项：商家确认信息和材料真实、完整、有效，并同意平台进行 AI 信息识别、必要的脱敏展示和电子存证。

商品名称、品牌和分类从当前商品生成服务端快照，不要求商家重复填写。供货证明支持 JPG、PNG、PDF，单文件不超过 10MB，PDF 最多 10 页；两张商品照片只支持 JPG、PNG，单张不超过 5MB。材料中与认证无关的价格、银行账号等信息允许预先遮盖；平台不要求填写采购成本。分类扩展只能依赖 `CATEGORY_1` 至 `CATEGORY_4` 编码，不能依赖可修改的中文分类名。

### 5.4 AI 输出与安全

模型必须返回经过服务端严格校验的结构化结果：

```text
decision: PASS / REJECT
confidence: 0.00 - 1.00
matchedFields
missingFields
riskFlags
merchantReason
publicSummary
materialValidUntil
```

- 商家上传的文档、图片文字和备注均是不可信输入，其中的指令不能改变认证规则。
- AI 不获得数据库写权限或业务工具权限，只返回判断结果，由服务端更新状态。
- 原始响应、系统提示词、密钥、异常堆栈和未经脱敏的材料不得返回前端。
- 原始材料必须使用独立私有目录或私有对象存储，不能复用商品公开图片地址。
- 保存文件哈希、商品快照、输入哈希、模型、提示词版本、置信度、处理时间和完整状态日志。

### 5.5 后端与异步处理

认证作为独立业务域实现，至少拆分：

```text
shop_product_certification
shop_product_certification_material
shop_product_certification_log
```

处理流程：

```text
商家提交并固化商品/材料快照
-> 创建持久化任务
-> 条件抢占并保持 PROCESSING
-> 图片/PDF识别和综合判断
-> 服务端校验结构化结果
-> 保存审计记录
-> PASSED / REJECTED
```

- 模型调用必须在业务事务外执行，支持限时、重试、幂等、应用重启恢复和失败追踪。
- `shop.product-certification` 与 `shop.ai-score` 保持各自独立的功能开关，启停互不联动。
- 两项 AI 功能共用 `spring.ai.dashscope` 下的 API Key、客户端和生成参数，通过不同提示词完成不同任务；各自的 `model` 保留在 `shop.ai-score` 和 `shop.product-certification` 下以便独立切换，商品认证调用时开启多模态模式，PDF 在服务端限制页数并转换为页面图像后交给模型识别。
- 商家接口同时按 `merchantId + productId` 校验；公开接口只返回 `PASSED` 的编号、时间、有效期和脱敏摘要。
- 表、唯一约束、任务、材料和日志均预留可信 `tenant_id` 隔离位置。

### 5.6 验收重点

1. 商家无法读取或修改其他商家的申请和材料。
2. 原始材料保持私有，消费者只能看到通过标识和脱敏摘要。
3. 超时、限流、非法 JSON 和应用重启不会误标通过或丢失申请。
4. 每次处理保留模型、提示词版本、输入哈希、理由和状态记录。
5. 只有 `PASSED` 商品公开展示认证标识。
6. 关键商品信息或材料变化后原认证失效。
7. 前端不存在本地假认证、随机结果或直接修改认证状态的逻辑。
8. 商城分页查询始终把有效 `PASSED` 商品排在未认证商品之前，失效后立即失去排序优先级。
9. 重新申请从上一版服务端数据回填且产生新的不可变申请记录，不覆盖历史审计记录。

## 6. 商品 AI 认证之后：外部赛事软件对接

后续与赛事软件开发人员共同完成：

1. 单点登录：用户从赛事软件跳转商城后免注册、免重复输入账号，由商城服务端校验一次性票据并自动创建或绑定商城用户。
2. 积分划拨：赛事软件保留历史总积分、尚未划出积分和划拨记录；积分通过唯一划拨单转入商城后，上游相应余额扣减或清零，商城负责后续消费、退款和冲正。

正式开发前必须确认外部用户唯一标识、票据交换、签名、划拨单字段、扣减或冻结时点、幂等、结果查询、重试和异常补偿规则。

- 长期登录令牌不能直接放在跳转 URL 中，不能仅靠手机号或昵称识别用户。
- 商城按“租户 + 来源系统 + 外部划拨单号”幂等入账，重复通知不得重复增加积分。
- 不能使用上游先清零、商城只接收一次通知且无法补偿的流程。
- 已成功流水不得删除或改写；退款、撤销和冲正保存独立反向流水。
- 外部身份按 `tenant_id + source_system + external_user_id` 唯一识别。

当前不实现单点登录、外部账号绑定或外部积分划拨，也不提前假设外部接口字段；现有积分消费仅限商城内部全平台通用券兑换。

## 7. 多租户 SaaS 约束

- 租户之间的用户、商家、商品、订单、甄客验、优惠券、积分和认证材料完全隔离。
- 隔离维度为租户间 `tenant_id` 加租户内现有 `merchant_id`。
- 租户身份必须来自可信登录令牌和服务端请求上下文，进入核心 Mapper SQL。
- 每个租户的微信商户号、公众号、AI 模型、支付、退款、查单和回调配置独立。
- 表结构、唯一约束、索引、缓存 Key、上传目录、任务和审计日志均需包含租户维度。
- 在统一租户上下文完成前，不接受前端 `tenantId`，不硬编码默认租户，也不局部添加无法形成真实隔离的伪租户字段。
- 正式多租户改造继续在当前模块化单体上分阶段实施，不默认迁移到其他商城框架。
