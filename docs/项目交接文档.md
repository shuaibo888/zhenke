# 甄客行项目开发交接

> 更新时间：2026-08-26
>
> 特别注意：本交接文档主要说明接下来要干什么，已经完成并验收的功能可以直接在本文档删除（此行禁止删除）。
>
> 当前实施口径：正式开始建设“甄客行”。甄客行不是以商城为主体的项目，而是一个类似大众点评的综合本地生活平台；第一阶段以平台首页和“甄客言”内容社区为主线，定位能力是核心基础能力。甄客行也不是另起炉灶的新系统，而是在现有商城已经形成的用户、商家、后台权限、交易和履约能力之上扩展出来的平台；现有商城作为甄客行内部的辅助交易模块继续完整保留和使用。

## 1. 产品定位与当前开发方向

甄客行面向本地居民、外地游客以及其他到访用户，承载城市内酒店、饭店、景区、商店和其他线下实体的发现、分享与点评。用户首先感知到的应当是一个综合本地生活平台，而不是一个被重新包装的商城首页。

当前阶段的产品主次关系如下：

1. **甄客行平台首页**：作为用户进入项目后的第一入口，承载轮播运营位、甄客言内容和必要的功能入口。
2. **甄客言**：作为第一阶段的核心内容功能，允许登录用户围绕酒店、饭店、景区、商店等本地实体发布帖子和点评。
3. **定位与地点**：作为甄客言及后续本地生活功能的公共基础能力，第一版先保证设备定位、当前市区显示、地点选择和导航正常；暂不使用定位结果过滤专区内容。
4. **用户视角身份**：发布甄客言时选择“本地土著”“外地人”等能说明体验视角的身份标签，帮助其他用户理解内容背景。
5. **商城**：保留现有完整交易能力，但弱化首页占比和平台心智，定位类似抖音、小红书中的商城——不是主体，但入口清楚、流程可用。

第一阶段目标是先把甄客行做出“本地生活内容平台”的基本样子和真实使用闭环，再根据实际业务逐步扩展酒店、饭店、景区等更深层的预订或交易能力。

### 1.1 以现有商城为底座扩展甄客行

甄客行的建设方式是“在现有业务底座上扩展平台能力”，不是“新建一套甄客行后再与商城对接”。界面首页、产品名称和用户心智会从商城升级为甄客行，但已经存在的身份、资产、交易和履约关系必须连续。

**所有现有商城用户天然就是甄客行用户。** 用户升级后不需要重新注册、重新绑定手机号、重新设置密码或迁移订单；新用户从甄客行注册后，也进入同一套用户体系，并同时具备使用甄客行内容能力和商城交易能力的基础身份。

| 业务对象 | 继续使用的现有底座 | 在甄客行中的扩展方式 | 明确禁止 |
|---|---|---|---|
| 消费者用户 | `shop_user`、现有登录注册、手机号绑定、用户资料和登录态机制 | 以同一个 `user_id` 增加甄客言、地点互动和后续内容关系 | 平行建设 `zhenke_user`，或让老用户重新注册、重新绑号 |
| 用户资产与历史 | 地址、积分、优惠券、订单、退款、试用、甄客验等既有数据关系 | 继续归属于原用户 ID，并在甄客行个人中心按业务类型展示 | 复制资产、迁移出新 ID，或切断历史订单与用户的关系 |
| 商家主体 | `shop_merchant`、既有入驻审核、商家资料、商品与履约能力 | 在需要时与甄客行地点建立经过审核的关联，并逐步扩展本地生活经营能力 | 为同一商家重复入驻，或仅凭名称自动认领地点 |
| 后台人员与权限 | `sys_user`、现有角色权限、商家后台绑定和操作审计 | 增加甄客言、地点、轮播和内容治理权限 | 把消费者 `shop_user` 与后台 `sys_user` 直接合并，或绕开现有 RBAC |
| 商城交易 | 商品、购物车、订单、支付、退款、试用、核销和甄客验状态机 | 作为甄客行内部可复用的交易与可信履约能力 | 另建一套重复订单中心，或用内容功能改写既有交易状态 |
| 地点与甄客言 | 复用现有用户、商家、媒体、地图和后台管理能力 | 通过最小新增表和关联字段建设地点、内容及管理模型 | 为了“平台化”批量重命名旧表、复制旧数据或提前拆分微服务 |

由此形成的产品关系是：甄客行是统一平台，商城是平台中的一个业务模块；用户身份是统一的，内容资格与交易资格按各自规则判断；商家、普通地点和可交易店铺可以有关联，但不是天然等同。

## 2. 核心产品概念

### 2.1 甄客言

“甄客言”是登录用户主动发布的本地生活内容。它可以围绕酒店、饭店、景区、商店或其他线下实体，也可以表达对某个地点的真实体验、推荐、避坑信息或观察。

甄客言当前确定的基本特征：

- 发布者必须是已登录用户。
- 发布时必须通过地址/地点选择器选择一个关联地点，地点是用户主动添加给帖子的定位信息。
- 关联地点由发布用户自由选择，不要求正文内容、用户当前位置、实际到访地点与所选地点一致。即使正文写的是天安门广场、用户选择的地点是东方明珠，也允许提交和发布；平台只记录用户选择，不把地点关联包装成“平台核实到访”或“内容与地点一致”的证明。
- 发布者可以额外选择关联一个已经入驻甄客行且状态正常的商家，但商家关联不是必填项。项目前期绝大多数甄客言预计只关联地点、不关联已入驻商家，产品和数据模型必须允许 `merchant_id` 为空。
- 已入驻商家必须由用户在商家选择器中主动选择，不能根据地点名称、地址或关键词自动绑定；地点与可选商家是分别保存的两种关联，选择其中一个不能自动推导另一个。
- 发布时必须选择一个用户视角身份标签，例如“本地土著”“外地人”等；正式选项和文案后续确认。
- 内容不局限于商城商品，也不要求发布者必须先在平台完成购买。
- 内容可以关联酒店、饭店、景区、商店以及后续接入的其他本地实体类型。
- 标题和正文必填；“建议”“优化建议”等补充字段不是必填项。
- 图片或视频至少上传一个，允许只上传图片、只上传视频或混合上传；不能沿用甄客验“必须至少有一张图片”的限制阻止视频-only内容。
- 首版媒体能力优先复用甄客验现有上传、预览和安全校验：资源总数最多 9 个、视频最多 1 个，图片支持 JPG/JPEG/PNG 且单个不超过 5MB，视频支持 MP4、单个不超过 10MB 且不超过 30 秒；后续原型若明确调整，再同步修改前后端规则。
- 用户应能在首页内容流中浏览甄客言，并进入独立详情页查看完整内容、作者视角和地点信息。
- 首版需要复用甄客验已有的评论与回复能力，不能把甄客言做成只能浏览、不能交流的静态帖子。
- 甄客言需要纳入超管后台管理。第一版不建设用户举报、商家申诉或恶意关联专项处理流程，由超管像管理现有甄客验一样查看并直接删除不适合继续展示的甄客言。

评分维度、话题、收藏、关注和推荐排序等细节，需在进入对应功能开发前继续确认，不能仅凭“类似大众点评”一次性照搬全部功能。评论已经确定进入首版；“有用”等甄客验现有互动能力应优先复用，具体产品文案可按甄客言语境调整。

### 2.2 甄客言与现有甄客验的区别

甄客言与甄客验是相关但不同的两类内容，不能直接合并为同一概念：

| 对比项 | 甄客言 | 甄客验 |
|---|---|---|
| 内容定位 | 面向本地生活实体的主动分享、点评和讨论 | 基于真实购买或试用履约形成的体验内容 |
| 发布资格 | 登录用户，不以平台订单为前提 | 继续按现有真实订单、试用、收货或核销资格判断 |
| 关联对象 | 地点必选；可以额外关联一个已入驻商家，但不绑定订单或商品 | 订单、商品或试用履约记录是可信资格来源 |
| 身份表达 | 发布时选择本地人、外地人等体验视角标签 | 继续突出已购买、已试用或已核销等履约背景 |
| 主要作用 | 丰富城市内容，帮助用户发现和判断本地实体 | 证明一段与平台交易或试用相关的真实体验 |

现有甄客验流程继续保留。后续可以讨论两类内容是否在同一个内容流中展示，但必须使用清楚的类型标识，不能把普通甄客言伪装成“已消费”或“已验证”内容。

两者的区别主要在发布资格与业务关联，不意味着重复建设两套完全不同的内容体验。甄客言应复用甄客验已经成熟的用户作者关系、标题与正文展示、图片/视频上传与预览、独立详情、直接分享、评论与回复、“有用”等适合普通内容的能力；但不能为了复用而把甄客言写入甄客验表、伪造订单或商品关系，或者把用户主动选择的商家关系显示成甄客验可信履约标识。

### 2.3 本地实体与地点

甄客行后续所有本地生活内容都需要围绕统一的“地点/实体”概念逐步建设。酒店、饭店、景区、商店首先是不同实体类型，不等于第一阶段必须同时建设四套独立交易系统。

地点能力至少需要表达：

- 地点名称、实体类型和公开地址。
- 经纬度以及地图服务使用的坐标体系。
- 所属城市、区县等必要地域信息。
- 地图选点、关键词搜索和当前位置附近选点。
- 地点详情与相关甄客言之间的关联。
- 用户端打开地图或导航的能力。
- 地点不存在、重复、迁址、停业或信息错误时的治理方式。

位置数据必须由后端按可信规则保存和校验，不能只依赖前端显示文本。涉及用户实时位置时必须先取得授权，并遵循最小采集、用途说明和隐私保护要求；公开帖子默认展示关联地点，不应直接暴露用户发布时的个人精确轨迹。

这里的“可信校验”只校验地点选择结果本身，例如地点标识、名称、坐标和地址字段是否来自允许的选择器或地图服务、格式是否有效，不校验正文语义是否与地点相符，也不证明用户实际到访过该地点。地点关联是用户声明，不是平台背书。

甄客言中的可选商家关联也属于用户主动声明。后端必须校验所选 `merchant_id` 对应的商家真实存在、已通过入驻审核且当前允许公开展示；该关联不代表商家认可内容、用户实际消费过或平台完成真实性认证。商家关联与地点关联分别保存，不能用商家门店地址覆盖用户选择的地点。第一版不为错误或恶意关联增加专门举报、申诉和自动判定流程；必要时由超管直接删除整篇甄客言。

### 2.4 用户视角身份标签

“本地土著”“外地人”等属于内容视角标签，用于说明发布者是以什么背景体验该地点，不是系统角色、后台权限或身份认证等级。

第一阶段原则：

- 发布甄客言时必选一个视角标签。
- 标签要短、易懂，并能帮助阅读者判断内容视角。
- 标签选项由平台统一维护，不能让用户任意输入后伪装成官方身份。
- 标签不授予商家管理、审核、核销或其他后台权限。
- 是否允许用户长期保存默认标签、每篇内容单独选择，以及是否需要认证“本地人”，进入详细设计时再确认。

## 3. 甄客行首页

甄客行首页替代“商城首页是项目唯一主入口”的旧口径。首页首版按以下信息层级设计：

### 3.1 左上角当前市区

首页左上角默认展示根据设备定位得到的当前市区，让用户明确感知甄客行具备真实定位能力：

- 首次需要定位时按浏览器或微信环境正常申请用户授权。
- 定位成功后显示当前市区，并保存业务需要的城市、区县和坐标信息。
- 定位失败、用户拒绝授权或地图解析失败时，需要提供明确提示和手动选择城市的降级方式，不能让首页无法使用。
- 第一版的当前市区主要用于位置展示、选点基础和后续能力准备，**不得据此过滤本地专区、外地专区或首页甄客言内容**。
- 用户在北京、邯郸或其他城市看到的专区内容，第一版不因设备当前位置不同而出现数量差异或空白专区。

### 3.2 轮播运营位

首页上方展示轮播图，用于平台运营和项目导流：

- 每个轮播项至少包含图片、标题、跳转类型、跳转目标、排序和启停状态。
- 可以跳转到甄客行内部页面，也可以跳转到经过后台配置和校验的其他项目链接。
- 赛事链接可以作为“其他项目外链”的示例，但这不代表赛事成为甄客行自身业务模块，也不在甄客行内建设赛事功能。
- 外链需要明确的安全校验、可用性检查和适合当前浏览环境的打开方式。
- 后台应能配置轮播内容、顺序、有效期和跳转目标，不能将运营链接长期硬编码在用户端。

### 3.3 甄客言专区与内容区

轮播图下方以甄客言为首页主体内容，让用户进入首页后直接感知城市生活内容。甄客言可以设置“本地专区”“外地专区”等专区入口，专区名称、样式和切换交互需要正常呈现。

项目启动初期采用冷启动内容策略：

- 本地专区、外地专区等专区可以正常进入和浏览。
- 第一版所有专区使用平台级内容池、运营内容池或后续明确的非地理分区规则，不按设备当前位置自动筛选。
- 第一版也不因为帖子关联了某个城市，就自动把它限制在该城市用户的本地专区中。
- 不能出现“邯郸内容较多，但北京用户进入本地专区后什么也看不到”的情况。
- 当前市区、帖子关联地点和专区内容分发是三个独立概念；前两项第一版真实可用，第三项暂不启用地域关联。
- 页面文案和交互不得声称已经实现“只看当前城市”或“附近真实内容”，避免向用户表达尚未实现的地域筛选能力。

首版至少需要形成以下闭环：

```text
浏览首页甄客言
-> 进入甄客言详情
-> 查看作者、视角标签和关联地点
-> 从地点信息进入地图或导航
-> 登录用户进入发布页
-> 选择地点和视角标签并提交内容
-> 内容真实保存后进入可展示状态
```

内容卡片和详情页需要优先突出内容本身、作者视角和地点关系。商城商品或购买入口只有在内容确实关联商品时才作为辅助信息出现，不能占据每条甄客言的主体位置。

### 3.4 功能入口

首页可以保留商城，并为酒店、饭店、景区等本地生活内容提供发现入口，但第一阶段不为了填满页面制作无真实数据、无真实页面的假模块。

入口设计原则：

- 甄客言和本地地点发现优先。
- 商城入口清楚但弱化，不再把商品瀑布流作为平台首页主体。
- 酒店、饭店、景区等入口先连接真实地点和内容；具备真实交易能力时再显示预订、购票或套餐能力。
- 所有入口使用正式路由和独立页面，刷新、分享和登录回跳后仍能恢复当前页面。

## 4. 甄客言首版业务闭环

### 4.1 发布

甄客言首版发布流程至少包括：

1. 检查登录状态，未登录用户完成登录后返回发布流程。
2. 用户通过地址/地点选择器自由选择一个关联地点；可以搜索其他城市或与当前定位无关的地点，不要求选择“附近地点”。
3. 用户可以跳过商家关联，也可以从已审核且状态正常的入驻商家中主动选择一个关联商家；不得按地点名称自动替用户选中。
4. 用户选择一个体验视角标签。
5. 用户填写必填标题和必填正文；“建议”“优化建议”等附加内容允许留空。
6. 用户至少上传一张图片或一个视频；允许视频-only内容，首版其余数量、格式、大小和时长限制复用甄客验媒体基线。
7. 前端进行必要提示，后端重新执行身份、字段、地点选择结果、可选商家状态、媒体和内容安全校验，但不得阻止已经明确允许的“正文与地点语义不一致”内容。
8. 保存内容及其作者、地点、可选商家、视角标签、发布状态和时间信息。
9. 第一版发布成功后进入公开展示状态；后续由超管在甄客言管理中查看并按需要直接删除。

发布成功必须以服务端真实保存结果为准，不能使用本地数组或仅修改前端状态模拟成功。

### 4.2 浏览与详情

- 首页和列表只展示符合公开条件的甄客言。
- 内容详情使用独立正式路由，支持刷新和分享后直接打开。
- 详情明确展示作者、发布时间、视角标签、关联地点和内容类型。
- 作者归属规则与现有甄客验保持一致：帖子持久化保存 `shop_user_id`，作者名称读取当前 `shop_user` 资料，优先显示昵称、没有昵称时显示账号名；用户后续更新昵称或头像时，历史甄客言按统一用户资料展示，不复制第二份作者账号。
- “我的甄客言”按服务端当前登录的 `shop_user_id` 查询，不能由前端传入任意用户 ID 查询或伪造作者归属。
- 账号停用与内容删除分开处理，继续遵循甄客验现状：停用账号不能继续登录发布或互动，但其已经公开的甄客言不会仅因账号状态变为停用而自动隐藏；超管仍可依据帖子自身公开/删除状态单独删除内容。
- 地点信息可以进入地点详情、地图查看或导航。
- 地点信息旁应明确表达“发布者选择的地点”，不能显示“到访认证”“平台核验”或类似误导性文案。
- 帖子关联了已入驻商家时，可以展示“关联商家”卡片并进入该商家的公开店铺或商品页；没有关联商家时不显示占位卡片，不因缺少商家关系影响内容完整性。
- “关联商家”只能表达用户选择的对象，不能显示为“商家确认”“商家官方评价”或“已消费认证”，也不能因此获得甄客验标识。
- 超管删除或地点失效后的内容应有明确状态，不能继续通过旧链接泄露。

### 4.3 评论与可复用互动

甄客言首版评论区按现有甄客验评论关系实现：

- 未登录用户可以浏览公开帖子及其公开评论；登录用户可以发表评论和回复。
- 评论作者从当前登录的 `shop_user` 获取，展示昵称、账号名和头像的规则与甄客验一致。
- 帖子发布者参与评论时显示“作者”标记，判断依据是评论 `shop_user_id` 与帖子作者 `shop_user_id` 相同。
- 用户只能删除自己发布的评论；删除一级评论时，其下回复一并隐藏，避免留下失去上下文的孤立回复。
- 评论正文必填，首版长度上限复用甄客验当前 500 字规则。
- “有用”、评论数量、分享、图片预览和视频播放等适合普通内容的现有能力优先复用；复用业务规则和组件，不要求甄客言与甄客验共用同一业务表。

### 4.4 超管后台甄客言管理

首版在现有管理端新增独立的“甄客言管理”，处理方式参考当前甄客验管理：

- 该功能面向超管，不向商家后台开放。
- 超管可以查看甄客言列表和详情，并按标题、作者、地点、可选关联商家、发布时间和状态等条件筛选。
- 详情需要能查看正文、图片、视频、作者、地点、可选商家、评论数量及必要的发布时间信息，避免只看摘要就误删。
- 超管可以直接删除公开甄客言。删除应采用明确的内容状态或逻辑删除，记录操作人和操作时间，删除后用户端列表、详情和分享旧链接均不可继续看到正文及媒体。
- 第一版不建设用户举报入口、商家举报或申诉入口、恶意关联专项处理、自动语义匹配和复杂审核工作流。
- 第一版不要求超管逐篇审核后才能发布；后面根据真实运营需求，再决定是否增加先审后发、举报、申诉、恢复、批量处理或自动审核能力。

评论已经进入首版，“有用”等现有互动优先复用；收藏、关注、评分体系和推荐算法是否进入首版，后续按明确优先级决定。这些扩展能力不能阻塞“发布—展示—地点关联—评论互动—超管删除”的最小真实闭环。

## 5. 商城在甄客行中的位置

现有商城既是甄客行中的辅助交易模块，也是甄客行继续建设所依赖的数据与工程底座，不能删除、废弃、复制或破坏。新的产品关系是“甄客行包含商城”，不是“商城等于甄客行”；首页弱化商城展示，不等于弱化现有用户、商家、订单和履约底座。

### 5.1 继续保留的能力

- 商家入驻、审核和公开店铺资料。
- 商品发布、审核、库存、购物车和优惠能力。
- 订单、支付、退款、发货、收货和线下核销。
- 线上/线下试用及其履约流程。
- 基于真实购买或试用资格的甄客验。
- 超管端和商家端已有管理能力。
- 现有用户账号、资料、地址、积分、优惠券和全部历史归属关系。
- 现有商家主体、商家后台账号绑定、审核状态和操作权限。

### 5.2 产品上的弱化方式

- 平台默认首页改为甄客行首页，不再默认展示完整商城首页。
- 商城保留独立正式入口和原有完整页面。
- 首页可展示少量与内容或运营主题相关的商品，但不能压过甄客言内容主线。
- 甄客言必须关联用户选择的地点，可以额外关联一个已入驻商家；第一版不关联商城商品或订单，商家关联也不能成为发布前提。
- 从甄客言进入商品购买时继续走现有可信订单、支付、退款和核销流程。

## 6. 用户、商家与地点关系

### 6.1 用户

现有商城用户不是“待迁移用户”或“商城侧用户”，而是甄客行的既有平台用户。甄客行上线后不做重复账号建设，也不要求用户为了使用首页、甄客言或地点能力重新开户：

- `shop_user` 继续作为消费者侧唯一主身份，保留现有用户 ID、账号名、手机号、密码、资料、状态和登录认证机制。
- 已有用户使用原账号登录甄客行；在正常登录态有效范围内，进入甄客行首页和商城不应再次登录。
- 甄客行新增注册、手机号登录或自动注册继续落到同一套 `shop_user`，不能出现“甄客行账号”和“商城账号”两套注册入口及两条用户记录。
- 甄客言作者、内容所有者、点赞评论等未来用户关系必须关联服务端当前登录的 `shop_user.user_id`，不得由前端自由指定用户 ID。
- 地址、积分、优惠券、订单、退款、试用、甄客验等历史数据继续属于原账号；升级产品首页和品牌不能改变这些数据的归属。
- 在同一账号下增加甄客言发布、内容管理和地点互动能力；内容专属资料优先使用扩展表或明确字段，不为内容功能复制一份用户主档。
- 用户视角标签是内容属性或用户偏好，不得混入后台 RBAC 权限。
- 用户个人主页后续需要区分其甄客言、甄客验和交易相关内容。
- 账号启停、手机号唯一性、账号名唯一性和登录安全继续沿用统一用户规则；内容下架、禁言等内容治理状态应与账号状态分层设计，不能用复制账号解决。

### 6.2 商家与普通地点

- 现有 `shop_merchant` 继续作为已入驻商家的业务主体，既有商家不因平台升级重复提交一套甄客行入驻资料。
- 现有商家后台继续使用 `sys_user` 与商家的既有绑定和 RBAC 权限；消费者账号、商家主体和后台操作员是不同概念，不得仅凭手机号或名称自动合并。
- 第一版商家后台不展示、不管理、不回复甄客言。甄客言不是商家商品的甄客验，也不是自动归属于某个商家的评价单。
- 用户端的公开甄客言仍可被普通用户浏览；商家人员如果以普通消费者身份使用用户端，与其他 `shop_user` 遵循同样浏览规则，但不获得“商家官方身份”或额外管理权限。
- 甄客言地点来自发布用户的地址/地点选择器。绝大多数地点可能属于尚未入驻平台的饭店、酒店、景区、门店或公共地点，不能要求先有 `shop_merchant` 才能选择和发布。
- 用户可以在发布时主动关联一个已审核通过且状态正常的 `shop_merchant`，但这是可选关系；未关联商家是项目前期的常态，不能影响发布、审核、展示和互动。
- 即使用户选择的地点恰好对应某个已入驻商家，也不能自动建立商家关联；只有用户明确选择商家时才保存可选 `merchant_id`。
- 即使甄客言明确关联了已入驻商家，也不会自动出现在商家后台、自动绑定商品或赋予商家查看、删除、回复或管理该帖子的权限。
- 第一版不从现有商家地址批量生成并自动认领甄客言地点。后续若需要把已入驻商家与地图地点关联，必须通过独立、可信、可审计的关联流程。
- “用户选择的地点”“平台已入驻商家”“可交易店铺”是不同状态，用户端必须使用清楚标识。

### 6.3 三类身份不得混淆

甄客行至少存在三类彼此有关联但不能混为一张用户表的身份：

1. **消费者用户**：以 `shop_user` 为主身份，浏览、发布甄客言并完成商城消费。
2. **商家业务主体**：以 `shop_merchant` 为主体，承载入驻资质、店铺、商品和履约责任。
3. **后台操作员**：以 `sys_user` 和现有 RBAC 为权限主体，执行超管或商家后台操作。

一个自然人未来可能同时具备多种身份，但必须通过明确、可审计的绑定关系表达，不能把三个主键当作同一个 ID，也不能由前端声明自己属于某个商家。第一版不提供“商家官方身份”发布、回复或管理甄客言的能力；普通甄客言始终按消费者 `shop_user` 身份发布和互动。

### 6.4 数据连续性与兼容边界

- 原有数据库表、主键和历史外键继续有效，新功能通过增量表、增量字段或明确关联表扩展。
- 不为了名称统一批量把 `shop_*` 表改成 `zhenke_*`，也不复制一份历史用户、商家、商品和订单数据。
- 原有商城路由、订单详情、甄客验详情、支付回调、分享链接和登录回跳在平台升级后仍需兼容。
- 新首页和新内容功能使用统一登录态；鉴权以服务端解析出的当前用户为准，不能依赖前端传入的作者、用户或商家身份。
- 甄客言与账号状态的展示关系复用甄客验：作者和评论归属于 `shop_user_id`，展示读取统一用户资料；账号停用不自动改变已公开内容状态，内容是否可见由帖子自身公开/删除状态决定。
- 数据库迁移只能新增版本化脚本，并为已有数据提供明确默认值、回填策略和回滚边界；未经确认不得做破坏性重构。
- 若新内容需要用户昵称、头像等展示信息，应读取统一用户资料并按公开规则返回；需要内容快照时必须明确快照用途，不能借此形成第二套用户主档。

## 7. 定位能力建设原则

甄客行后续会高度使用定位，因此定位不能只作为发布表单中的一个普通文本框处理。

当前建设原则：

1. 统一封装浏览器、微信环境和地图服务之间的定位与坐标转换。
2. 区分“用户当前定位”“用户选择的地点”“帖子公开展示的地点”，三者不能混为一个字段。
3. 发布甄客言时保存关联地点的稳定标识，并保存业务需要的地点快照，避免地点改名后历史内容无法理解。
4. 前端定位失败、拒绝授权或精度不足时，应允许用户通过地图或关键词手动选点。
5. 后端校验地点存在性、坐标格式和关联权限，不能信任用户提交的地点名称与坐标组合。
6. 对用户位置采用最小权限、最短必要保存和明确用途说明，不记录与业务无关的持续轨迹。
7. 未来的附近内容、距离排序、城市切换和区域筛选应复用同一套地点基础能力。

### 7.1 第一版定位与专区解耦规则

第一版必须同时满足“定位是真的”和“专区不按定位过滤”：

```text
设备定位 -> 首页左上角显示当前市区，并服务于发布选点、地点详情和导航

本地专区 / 外地专区 -> 正常展示甄客言，但暂时不读取设备城市作为内容筛选条件
```

实现时不能为了省事返回假城市，也不能因为已经拿到真实城市就提前给专区 SQL、接口或前端列表增加城市过滤条件。接口和数据模型可以保留未来地域分发所需的城市、区县和地点字段，但第一版专区查询默认使用全平台可展示内容范围。

后期只有在帖子数量和城市覆盖能够支撑稳定内容供给后，才启动真正的本地专区。启用前需单独确认内容量门槛、城市切换、当前位置与用户手选城市的优先级、无内容时的跨城兜底以及历史帖归属规则，不能仅通过打开一个城市筛选开关直接上线。

项目现有腾讯地图地址解析、商家详情和导航能力可作为基础，但在复用前必须检查其当前接口范围、浏览环境兼容性和位置隐私边界。

## 8. 第一阶段范围

### 8.1 第一阶段应完成

- 甄客行平台首页及正式路由。
- 首页左上角真实定位并默认显示设备当前市区，同时提供失败后的手动选择降级。
- 后台可配置的首页轮播图和内外部跳转。
- 甄客言列表、独立详情页和登录用户发布页。
- 本地专区、外地专区等专区入口和正常内容展示，但专区查询暂不关联设备定位或帖子所在城市。
- 地点搜索、定位选点、地点关联及必要的地图/导航入口。
- 发布时必选的用户视角身份标签。
- 必填标题、必填正文、可选建议，以及至少一个图片或视频的甄客言发布规则。
- 必选地点和可选已入驻商家的独立关联规则；没有商家关联是允许且常见的正常状态。
- 甄客言评论、回复、作者标记、用户自删评论及适合普通内容的现有互动能力。
- 甄客言的服务端真实保存、公开状态、逻辑删除状态和超管管理入口。
- 首页从商城主导调整为甄客言主导，同时保留商城正式入口。
- 现有甄客验与甄客言在概念、资格和展示标签上的明确区分。
- 现有商城用户使用原账号直接进入甄客行，并能在同一账号下继续查看原有订单、资产和甄客验。
- 甄客行新增用户进入现有统一用户体系，注册后既能使用甄客言，也能进入商城交易流程。
- 已入驻商家和后台操作员继续使用现有商家主体、账号绑定和权限体系，不重复入驻、不重建后台账号。

### 8.2 暂不因本轮需求自动扩展

- 完整照搬大众点评的所有评分、榜单、会员、广告和推荐算法。
- 同时建设酒店选房、景区实名票务、饭店订座排队等完整交易系统。
- 仅为了平台化而大规模重命名现有数据库表或拆分现有商城代码。
- 跨城市运营体系、城市加盟体系和完整多租户改造。
- 未确认规则的达人认证、本地人认证、等级成长和商业推广体系。
- 将轮播外链所指向的其他项目建设成甄客行内部业务模块。
- 第一版不启用“本地专区只显示当前城市帖子”、附近距离排序或按城市隔离内容池。

多租户仍放在较后阶段。只有平台、内容、地点和多个真实业务模块稳定后，才能基于可信租户上下文设计数据库、权限、配置、缓存、文件、任务和审计隔离。

后端继续采用模块化单体，标准调用方向为：

```text
controller -> service -> mapper/XML -> domain/dto/vo
```

开发约束如下：

- 先检查现有用户、媒体、地图、商家、审核、评论和甄客验能力，再决定复用或增加最小新模型。

- 甄客言必须使用真实后端接口和持久化数据，不得使用 mock、本地数组或仅修改前端状态模拟成功。
- Controller 负责接口和基本参数接收，Service 负责身份、事务、资格和状态，Mapper SQL 负责归属、期望原状态和并发条件。
- 用户身份、地点、商家关系、审核状态和目标状态均不能信任前端提交，必须由服务端重新确认。
- 新页面使用正式独立路由和页面文件，保证刷新、分享、登录回跳和浏览器前进后退可用。
- 不破坏现有商城历史数据、订单、支付回调、退款、分享链接和核销闭环。
- 数据库变更只新增版本化增量脚本，不改写已执行的历史脚本；是否保留脚本按当前项目约定执行。
- 上传媒体、定位数据、用户资料和联系方式必须最小化公开，并在服务端落实访问权限。
- 工作区现有未提交代码均视为用户有效改动，不清理、不重置、不覆盖、不混入无关提交。
- 未经当前对话明确授权，不执行数据库变更、部署或生产环境操作。

## 10. 推荐实施顺序

### 阶段一：确认产品细节与现有能力

1. 确认甄客言首版字段、媒体规则、身份标签选项、公开发布和超管删除规则。
2. 盘点 `shop_user`、`shop_merchant`、`sys_user` 及订单、资产、试用和甄客验的现有归属关系，形成不可破坏的兼容清单。
3. 检查现有登录、用户、上传、地图、内容、分享和管理端能力。
4. 明确首页首版信息架构和移动端优先的页面结构。
5. 明确地点来源、腾讯地图能力、坐标体系和用户隐私提示。
6. 把“老用户原账号可直接使用甄客行、新用户与商城共用账号、历史资产不丢失”纳入首版验收用例。

### 阶段二：地点与甄客言最小闭环

1. 建立统一地点模型或在现有可信模型上补齐地点能力。
2. 完成甄客言后端模型、接口、公开/删除状态和超管管理入口。
3. 完成甄客言列表、详情、发布、地点选择、可选商家选择、身份标签、媒体预览和评论互动。
4. 验证登录回跳、视频-only发布、仅地点不关联商家、主动关联已入驻商家、自由地点选择、评论回复与自删、定位失败降级、发布展示、超管删除和删除后的旧链接状态。

### 阶段三：首页与平台心智

1. 将用户默认首页调整为甄客行平台首页。
2. 接入可配置轮播图及安全的内外链跳转。
3. 让甄客言成为首页主体，正常展示本地专区、外地专区等入口，但使用不按定位过滤的冷启动内容池。
4. 将商城调整为辅助入口，保留原有完整业务链路。

### 阶段四：持续扩展

- 根据真实使用情况增加评论、点赞、收藏、关注、评分、搜索和附近内容。
- 当内容量和城市覆盖达到另行确认的门槛后，再将本地专区与用户当前城市或手选城市关联。
- 根据业务优先级深化酒店、饭店、景区等实体详情与交易能力。
- 在内容和交易关系稳定后再讨论推荐算法、商业化和跨城市运营。
- 多租户最后实施，不为远期设想提前建设空表、空接口和通用框架。

## 11. 开发前仍需确认的关键问题

在开始大规模改代码前，至少需要继续确认以下产品细节：

1. 甄客言是否需要星级或分项评分，还是首版只做帖子内容。
2. 用户视角身份标签的正式选项，以及每篇单独选择还是保存默认值。
3. 帖子公开展示地点名称和地址到什么精度，是否显示用户与地点的距离。
4. 地址/地点选择器使用腾讯地图的哪个 POI 接口，地点快照、重复地点和地点纠错如何处理。
5. 除评论和“有用”外，甄客言首版是否包含收藏、关注和分享，各自优先级如何。
6. 首页除轮播图和甄客言外，第一版确定保留哪些入口和栏目。
7. 外部项目链接允许哪些域名、在微信和普通浏览器中分别如何打开。
8. 第一版本地专区与外地专区是共用平台内容池，还是采用人工运营的非地理内容分区。

当前需求的默认结论是：**甄客行以现有商城系统为业务与工程底座扩展，所有现有商城用户直接成为甄客行用户，新用户与商城共用同一套 `shop_user`；现有商家、后台权限、用户资产、订单、支付、退款、试用、核销和甄客验关系继续复用且不得破坏。甄客言复用甄客验的用户归属、作者展示、媒体、评论、分享和适合普通内容的互动能力，但不绑定订单或商品；标题和正文必填、建议可选、图片或视频至少一个。地点必选，用户可以自由选择任意地点，平台不校验正文与地点是否一致；已入驻商家可选且只能由用户主动选择，没有商家关联是项目前期的正常状态。即使关联商家，甄客言也不会变成甄客验，第一版商家后台仍看不到也不能管理甄客言；账号停用不自动隐藏既有公开内容。第一版不做举报、商家申诉、恶意关联专项处理和复杂审核流程，用户发布后公开展示，超管后台新增甄客言管理并可像现有甄客验管理一样直接逻辑删除。立即启动甄客行平台首页与甄客言主线设计；首页左上角必须真实定位并显示当前市区；本地专区、外地专区第一版正常展示但不与设备定位或帖子城市关联，统一采用冷启动内容策略；商城完整保留但降为辅助模块；其他项目可以通过轮播外链导流，但不自动成为甄客行内部业务。**
