## 0. 需求依据与视觉基准

发生冲突时按以下顺序判断：

1. 当前任务中用户的最新明确要求。
2. 本文仍保留的产品和安全边界。
3. 仓库中的真实路由、接口、数据模型和历史兼容关系。
4. 正规工程中的安全性、可用性、响应式、无障碍和可维护性原则。
5. `yuanxing/` 只提供视觉方向，不提供业务或技术契约。

`yuanxing/` 是只读概念原型。正式用户端继续采用白色主画布、暖橙主操作色、深色文字、摄影内容、克制的圆角与阴影，以及紧凑但不拥挤的移动端节奏；绿色只用于成功、安全等语义状态。不得复制原型的原生 HTML、全局脚本、Hash 路由、Mock 数据、模拟登录/支付/订单、硬编码城市或演示图片选择器。

赛事只允许作为后台轮播配置的外部链接，不是甄客行内部业务。原型中的关注、收藏、赛事套餐、数字人民币、区块链、区域运营等内容不会自动成为需求。

## 1. 平台定位、身份与兼容边界

甄客行是综合本地生活平台。首页、甄客帖和地点发现是用户主心智；商城是平台内完整的交易模块，而不是平台首页主体。系统是在现有商城底座上扩展，不新建平行账号、商家、订单或支付体系。

| 对象 | 当前唯一主体 | 长期边界 |
|---|---|---|
| 消费者 | `shop_user` | 原用户直接成为甄客行用户；账号、资料、地址、积分、优惠券、订单、试用和甄客验继续归属原用户 ID |
| 商家 | `shop_merchant` | 继续使用原入驻、审核、商品和履约关系；普通地点不等于已入驻商家 |
| 后台操作员 | `sys_user` + RBAC | 超管与商家权限继续分离，不与消费者 ID 混用 |
| 交易 | 原商品、购物车、订单、支付、退款、核销体系 | 原商城能力完整保留，新增本地生活分类复用同一状态机 |
| 内容与地点 | 独立甄客帖、甄必享和地点模型 | 不写入甄客验主表，不伪造订单、消费或到访资格 |

现有商城用户不重新注册或绑号，新用户也进入同一套 `shop_user`。原订单、支付回调、退款、核销、试用、甄客验和历史分享链接必须保持兼容。消费者、商家主体和后台操作员即使属于同一自然人，也只能通过明确、可审计的关系连接，不能把三类主键视为同一 ID。

用户端移动导航固定为“首页 / 甄客帖 / 商城 / 我的”。全站只有一个 `/profile`，不再建立独立的“商城个人中心”。悬浮“发布甄客帖”只在首页和甄客帖主列表展示；个人中心、交易流程、官方甄必享、详情页、表单页和异常页不展示。地点与甄必享详情使用带地点上下文的页内发布入口。

## 2. 三类内容与互动

| 类型 | 发布主体与资格 | 核心关联 | 当前互动 |
|---|---|---|---|
| 甄客帖 | 登录用户主动发布，不要求平台订单 | 必选地点，可选已审核商家，必选内容视角 | 评论、回复、“有用”、分享、作者删除、超管删除、站内信 |
| 甄客验 | 继续由真实订单、试用、收货或核销资格产生 | 商品、订单或试用履约 | 保留原有可信体验与互动能力，并产生用户级站内信 |
| 甄必享 | 仅超管运营的官方地点专题 | 地图确认的真实地点及独立专题资源 | 用户可浏览、点赞、评论、回复和删除自己的评论；当前不产生站内信 |

### 2.1 甄客帖

- 发布时必须选择“本地土著 / 外地游客 / 在外家乡人”之一。它是每篇内容相对于所选地点城市的视角标签，不是认证等级或系统权限。
- 地点必选，商家可选；两者都是用户主动声明。正文可以与地点语义不一致，平台不把地点关联表达成实际到访、消费认证或官方背书。
- 可选商家只能从审核通过、状态正常且允许公开展示的 `shop_merchant` 中主动选择，不能根据名称或地址自动绑定。
- 标题和正文必填，建议字段可选。至少上传 1 张图片；图片和视频合计最多 9 个，视频最多 1 个。图片支持 JPG/JPEG/PNG、单个不超过 5MB；视频支持 MP4、单个不超过 10MB 且不超过 30 秒；不允许只上传视频。
- 发布结果必须以服务端持久化为准。作者可以逻辑删除自己的帖子，但当前不编辑或恢复已发布帖子；超管可以查看并逻辑删除不适合继续展示的内容。删除后列表、详情和旧分享链接均不得继续返回正文与媒体。
- 账号停用会阻止后续登录、发布和互动，但不会自动隐藏该账号此前公开的帖子；内容是否可见仍由帖子自身的公开与删除状态决定。
- 作者、评论者、删除者和“有用”用户均由服务端当前登录的 `shop_user` 推导，前端不能指定用户 ID、计数或内容归属。

### 2.2 评论与站内信

- 公开内容和公开评论可匿名浏览；登录用户可以评论和回复，且只能删除自己的评论。删除一级评论时，其回复一并隐藏。
- 甄客帖与甄客验的评论、回复使用服务端分页；评论归属、“有用”状态及并发更新均由服务端校验，不能一次加载无限评论树或相信前端状态。
- 别人对用户的甄客帖或甄客验标记“有用”、发表评论，或者回复该用户的评论时，系统生成持久化站内信。
- 收件人由真实内容作者和回复目标推导；自互动不提醒，同一行为使用稳定去重键避免重复投递。回复目标与内容作者不同时，可分别通知。消息写入与对应的评论、回复或“有用”变更处于同一事务，不能产生只有互动没有消息或只有消息没有互动的半完成状态。
- “我的—消息中心”提供未读数、分页列表、单条已读和全部已读。内容删除后可保留消息快照，但目标跳转仍服从详情权限和删除态。
- 当前由超管维护的甄必享不发送站内信。

### 2.3 甄必享

甄必享与甄客帖、商品均相互独立，固定按“甄必玩 / 甄必吃 / 甄必住 / 甄必购”展示，对应稳定代码 `SCENIC / RESTAURANT / HOTEL / MALL`。首页每类只展示最新 2 条，完整内容进入独立“查看更多”分页列表。

专题必须由超管通过地图 POI 选择真实地点，服务端根据地图提供方地点 ID 再次确认并保存统一地点。专题必须维护地点标题、1 至 9 张有序图片、服务摘要和详细攻略，地址来自真实地点；开放时间和公开电话可选。普通用户不能新增、编辑、投稿或把甄客帖归入甄必享。从专题发布甄客帖只带入地点，不产生投稿或官方背书关系。

未来可以另行评估把优质用户甄客帖形成“必吃榜”等榜单，但上线前必须定义周期、城市和品类、有效互动权重、反作弊、内容安全、申诉及人工运营规则。当前官方甄必享不能直接改成用户榜单。

## 3. 首页、定位与城市内容范围

首页依次承载当前城市、后台轮播、横向甄客帖故事流和四类纵向甄必享。商城保留清楚入口，但商品瀑布流不能重新成为首页主体。公开帖子按发布时间倒序；完整帖子流只按三种内容视角切换，卡片展示帖子真实地点城市，公共内容范围按下述城市开关处理。

位置相关概念必须分开：

- 当前定位或手选城市：用于页头显示、地点选择、地图导航，以及城市开关开启后的公共内容范围。
- 帖子关联地点：用户为单篇帖子选择并公开展示的地点。
- 内容视角：发布者与该帖地点城市的关系，不代表设备当前位置。

浏览器和微信入口均应尝试真实定位；拒绝、超时或地图服务失败时页面继续可用，并提供手动选城。用户主动手选后，迟到的自动定位不能覆盖其选择。系统只保存业务需要的当前会话位置，不记录无关的持续轨迹。

公共列表范围只服从 `sys_config` 参数：

```text
shop.zhenkexing.cityFilterEnabled 缺失或 false
-> 甄客帖、甄必享公共列表展示全平台内容

shop.zhenkexing.cityFilterEnabled = true
-> 两类公共列表按当前定位或手选城市过滤
-> 缺少当前城市时明确失败，不得静默回退全平台
```

三种帖子视角始终是城市范围内的独立条件。帖子详情、甄必享详情和指定地点内容不受公共列表城市开关限制。

后端地图密钥 `TENCENT_MAP_KEY` 与腾讯 URI 导航的 `TENCENT_MAP_REFERER` 必须分开配置；后者是腾讯位置服务控制台登记的应用名，两者不可混用，也不得写入前端或仓库。轮播外链只允许带有效主机名、不含用户凭据的完整 `https` 地址，不设置业务域名白名单。

永久内容分享继续使用干净的同源 ID 路径：`/posts/{id}`、`/products/{id}`、`/reports/{id}`、`/enjoy/{id}`；试用仍使用 `/products/{productId}?campaign={campaignId}`。任务型子页应提供明确的安全父页返回，分享直达或刷新时不能因缺少站内历史而退出项目或形成无效返回。

## 4. 四大交易模块与统一“我的”

用户侧交易入口并列为“商城 / 酒店 / 景区 / 饭店”：

- “商城”完整聚合原有动态分类、自营与商家商品、试用、购物车、线上购买、支付、配送、原有线下核销、退款和甄客验。它不是第四条数据库分类，也不能被三个新增分类替代。
- 酒店、景区、饭店使用稳定分类代码 `ZHENKE_HOTEL`、`ZHENKE_SCENIC`、`ZHENKE_RESTAURANT`，不能依赖数据库自增 ID 或中文名称判断业务。
- 三个新增分类复用原商品、订单、支付、商家核销和甄客验资格链路，由服务端在商品保存、上架、结算和下单时强制 `OFFLINE` 履约。
- 酒店、景区和饭店商品必须真实维护套餐内容、使用须知、有效期、预约要求与说明、退款及过期规则；前后端数据契约保持一致，并由服务端复核。
- 普通商城商品继续服从原有线上配送、线下核销或两者兼有的配置，不得被新的分类规则统一改写。
- 有限库存继续原子扣减并按订单实际扣减快照回补；无限库存经过同一校验入口但数量不因售卖减少。
- 第一版不另建房态日历、桌位预订、实名票务、多规格 SKU 或多次核销系统；真实业务出现后再扩展统一交易底座。

唯一 `/profile` 统一承载身份资料、我的甄客帖、甄客验、消息中心、订单与核销、优惠券、积分、试用、地址和账号安全。订单状态按用户任务表达为待付款、待使用、待收货、售后和已完成；线上物流与线下核销继续由同一订单体系按履约类型区分。积分明细从“我的”进入时返回“我的”，从积分中心进入时返回积分中心；无来源直达默认返回积分中心。

## 5. 当前路由与管理边界

| 领域 | 主要用户端路由 |
|---|---|
| 首页与内容 | `/`、`/posts`、`/posts/:postId`、`/posts/publish`、`/enjoy`、`/enjoy/:enjoyId`、`/places/:placeId` |
| 交易 | `/mall`、`/mall/products`、`/mall/content`、`/products/:productId`、`/merchants/:merchantId`、`/checkout` |
| 个人中心 | `/profile`、消息、帖子、甄客验、订单、积分、优惠券、试用等 `/profile/**` 子路由 |
| 认证与异常 | `/auth`、`/sso/callback`、404 |

管理端正式基路径为 `/admin/`：

- 甄客帖管理、甄必享管理和首页轮播管理只向超管显示并开放接口，必须同时校验角色和独立动作权限。
- 商家继续管理自己的商品、订单和核销，不获得用户内容管理权限。
- 甄必享新增或编辑不直接改变发布状态；发布、下线和删除使用独立权限动作。
- 轮播支持完整新增、编辑、删除、排序、有效期和启停，不在用户端硬编码运营内容。

## 6. 工程、数据与交付安全

| 模块 | 目录与职责 |
|---|---|
| 用户端 | `delivery-frontend`：React 19、Umi 4、Ant Design 6 |
| 管理/商家端 | `delivery-admin-frontend`：同技术栈，基路径 `/admin/` |
| 后端 | `delivery-backend`：Spring Boot 3.5、Java 17、Maven 多模块单体 |
| 核心业务 | `delivery-backend/ruoyi-shop`：商城、甄客行内容、地点与互动 |

后端保持 `Controller -> Service -> Mapper/XML -> domain/dto/vo` 分层。身份、资格、事务和状态机在 Service 校验；资源归属、期望原状态和并发条件同时落实到 Mapper SQL。前端传入的用户、商家、价格、库存、订单状态、作者、审核状态、地点名称和坐标都不可信。

正式页面只读取真实 API 和持久化结果。API 业务成功以响应体 `code === 200` 为准，不能只看 HTTP 状态；列表通常为 `{ rows, total }`。加载、空态、失败、权限、删除、分页、刷新、分享和登录回跳都必须保留可恢复行为。

媒体新数据只保存 `/profile/...` 平台根相对路径；服务端校验格式、大小、数量、目录归属、真实文件和路径穿越。前端只提供本地文件选择或拖拽上传，不提供媒体 URL 手填入口。用户位置、头像、联系方式和其他个人信息按最小权限返回。

当前 `delivery-backend/migrations/` 没有待执行脚本。用户已确认目标数据库更新已经执行，并按项目约定删除已应用脚本；不得恢复、重跑或改写这些历史迁移。后续结构变化必须创建新的、未使用过的版本化增量脚本，并由负责人手动执行。当前消息写入依赖目标库已经存在 `shop_notification` 表。

未经当前任务明确授权，不连接或修改生产数据库，不执行迁移，不部署或重启生产服务，不写入真实密钥，不删除生产数据。普通 Cloud 验证使用 `-Dcodex.cloud=true` 排除 PCC 运行时依赖；生产打包不得使用该参数。

常用验证命令：

```bash
npm --prefix delivery-frontend run typecheck
npm --prefix delivery-frontend run build
npm --prefix delivery-admin-frontend run typecheck
npm --prefix delivery-admin-frontend run build
mvn -f delivery-backend/pom.xml -Dcodex.cloud=true -pl ruoyi-shop -am test
git diff --check
```

构建、数据库迁移、真实账号业务、地图/微信/支付联调和生产运行是不同证据，不能互相替代。工作区已有改动视为用户有效内容；只暂存本任务已审查文件，不使用 `git add -A`，不自动合并或推送 `main`。本次交付目标为 GitHub PR #7，其真实源分支已核对为 `codex`，更新时使用非强制推送到该分支。

## 7. 当前不做与后续方向

当前没有已知第一版代码待办。新增需求继续以用户最新指示为准，以下能力不会因为竞品或原型存在而自动扩张：

- 收藏、关注、星级/分项评分、话题、个性化推荐和商业广告体系。
- 酒店房态、饭店排队订座、景区实名票务、多次核销和复杂 SKU。
- 用户举报、商家申诉、自动审核和复杂内容风控工作流。
- 附近距离排序、城市加盟、多租户和跨城市运营体系。
- 把赛事或其他轮播外链项目改造成甄客行内部模块。
- 把当前超管甄必享直接改成用户内容榜单。

若后续启动用户榜单、垂直预订、多租户或城市运营，先补齐业务规则、权限、数据迁移、反作弊和真实验收标准，再进入实现。
